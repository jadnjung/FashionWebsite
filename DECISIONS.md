# Esque — Decisions

An ADR-style record of durable technical/product decisions and why they were made. See [PROJECT.md §77](./PROJECT.md) for the recommended format. Append new decisions at the bottom; don't rewrite history — if a decision is reversed, record the reversal as a new entry and note which prior entry it supersedes.

---

## D-001 — Use Shopify as the commerce backend

**Decision:** Shopify (Basic plan) handles products, variants, pricing, inventory, collections, customer records, orders, discounts, payment processing, checkout, and fulfillment data. The custom frontend never re-implements any of this.

**Reason:** Reliable inventory, checkout, payments, order management, and product operations without forcing the team to build or maintain that infrastructure. See [PROJECT.md §50–53](./PROJECT.md#50-commerce-platform-recommendation).

**Alternatives considered:** Stripe-only — rejected because it would require building product management, inventory, order management, discounts, customer commerce history, fulfillment, returns, merchandising, and commerce analytics from scratch. Unnecessary engineering work for V1.

---

## D-002 — Headless Next.js frontend instead of Shopify Hydrogen/Remix

**Decision:** The storefront is a standalone Next.js (App Router, TypeScript) application talking to Shopify via the Storefront API, rather than using Shopify's Hydrogen/Remix framework.

**Reason:** Hydrogen provides built-in commerce primitives but couples the project to Remix conventions and Shopify's own hosting (Oxygen). [PROJECT.md §51](./PROJECT.md#51-frontend-architecture) explicitly cautions against coupling Esque "so tightly to experimental framework features that upgrading becomes difficult." Next.js gives more control over the experimental animation/interaction system (custom cursor, shared-element transitions, the interactive model) and has a larger ecosystem for that kind of work. Confirmed with the project owner 2026-08-17.

---

## D-003 — Hosting on Vercel

**Decision:** Deploy the Next.js storefront to Vercel.

**Reason:** Best-in-class Next.js support (edge rendering, image optimization, preview deployments per PR). Follows naturally from D-002 — Shopify Oxygen is only relevant if using Hydrogen. Confirmed with the project owner 2026-08-17.

## D-004 — pnpm as the package manager

**Decision:** Use pnpm exclusively; do not introduce npm or yarn lockfiles.

**Reason:** `pnpm-lock.yaml` already exists in the repository. Per global engineering guidelines, don't introduce a second package manager without cause.

## D-005 — Access gate is a UI-layer experience, not an SEO wall

**Decision:** The password gate blocks human navigation in the UI but does not prevent product/collection routes from being server-rendered, indexed, and crawled.

**Reason:** [PROJECT.md §80](./PROJECT.md#80-important-access-gate-seo-rule) is explicit: "The password experience must not prevent search engines from discovering the product catalog... The gate should therefore function primarily as a visitor experience rather than a server-level wall." Blocking crawlers at the server/middleware level would kill organic search visibility for the entire catalog, which conflicts with the SEO requirements in [PROJECT.md §79](./PROJECT.md#79-seo).

---

## D-006 — Layered motion stack, not one animation library for everything

**Decision:** Use native CSS transitions/transforms as the default, View Transitions where the browser supports them, a Framer-Motion-style library for component/layout motion, GSAP only for complex sequences that justify it, and Three.js/WebGL only for isolated high-impact features once real assets exist to justify them.

**Reason:** [DESIGN_SYSTEM.md §62](./DESIGN_SYSTEM.md#62-recommended-frontend-motion-stack) explicitly warns against using three animation systems to solve the same problem — each library adds bundle weight, and Esque's performance priority order ([PROJECT.md §75](./PROJECT.md#75-performance)) puts usability and perceived speed above animation sophistication.

---

## D-007 — Collections and Categories are modeled as separate dimensions

**Decision:** A product's Collection (which drop it belongs to, e.g. "Collection 001") and its Category (what it is, e.g. "Tops / Hoodies") are stored and queried independently — Collection via a Shopify Collection + drop-status metafields, Category via product type/tags.

**Reason:** [PROJECT.md §10](./PROJECT.md#10-collections-vs-categories) requires these to "remain separate" as a hard product rule; conflating them would make it impossible to browse "all Hoodies across every collection" or "everything in Collection 001 regardless of category" independently.

## D-009 — Disable Next.js automatic "agent rules" file generation (`agentRules: false`)

**Decision:** Set `agentRules: false` in `next.config.ts`.

**Reason:** Next.js 16.3+ auto-generates/appends a managed block to `CLAUDE.md` and `AGENTS.md` on every `next dev` run — including the dev server Playwright's `webServer` boots for every E2E test run, which is nearly every task in this build. The appended block itself contains text directed at AI agents instructing them to commit it. This project treats `CLAUDE.md` as never to be modified except by explicit human instruction; this auto-generation behavior was observed live twice in one build session (once during an early implementer dispatch, again during Task 3's Playwright setup) before being closed off here — each time correctly caught and reverted before commit, never landed in history, but a structural risk that would otherwise have recurred on every remaining task. `agentRules: false` is Next.js's own documented opt-out, not a workaround — confirmed against current official docs ([`vercel/next.js`, `docs/01-app/02-guides/ai-agents.mdx`](https://nextjs.org/docs/app/guides/ai-agents)) via Context7 before applying, and verified empirically afterward: with the flag set, a live `next dev` server leaves both `CLAUDE.md` and `AGENTS.md` untouched (`git status` clean, `git diff -- CLAUDE.md` empty, `AGENTS.md` not created).

## D-010 — Focus-ring color is `--color-esque-text`, not `--color-esque-forest`

**Decision:** Every focus-visible outline in this project — the global CSS safety net in `app/globals.css`, and every component-level focus ring, including Button (Task 7) — uses `--color-esque-text` (`#F3F1EA`), never `--color-esque-forest` (`#1F3D2B`) or `--color-esque-forest-highlight` (`#335B41`).

**Reason:** [DESIGN_SYSTEM.md §22](./DESIGN_SYSTEM.md#22-custom-cursor) and [PROJECT.md §78](./PROJECT.md#78-accessibility) require visible focus states meeting WCAG 2.2 AA. Computed contrast (WCAG 2.1 relative-luminance formula, verified independently, not just asserted): forest vs. `--color-esque-black` ≈1.71:1, forest vs. `--color-esque-surface` ≈1.65:1, forest-highlight vs. black ≈2.63:1 — all fail WCAG 1.4.11's 3:1 minimum for non-text/focus indicators. `--color-esque-text` reaches ≈18:1 against both backgrounds, comfortably passing, and keeps focus rings within the palette's 80%-monochrome identity ([DESIGN_SYSTEM.md §5](./DESIGN_SYSTEM.md#5-color-usage-rule)) rather than introducing a new color. This does not change the palette itself — forest remains correct for its other documented uses (selection states, active states, rare emphasis); the fix is scoped to focus-ring visibility specifically. Discovered during Task 5's task review: the plan's own text specified forest for this purpose (inherited from the original design spec, not an implementer error), and the same defect appeared again in Task 7's planned Button component text — both corrected under this ruling before either landed.

## D-011 — Tailwind CSS as the styling approach, configured via CSS `@theme`

**Decision:** Use Tailwind CSS v4 for all styling. Design tokens (colors, type scale, spacing, letter-spacing, easing) are declared in a single `@theme` block in `app/globals.css`, not a separate `tailwind.config.ts`.

**Reason:** Resolves the open item in [ARCHITECTURE.md §10](./ARCHITECTURE.md#10-open-architecture-decisions). Tailwind v4's current convention is CSS-first configuration — there is no JS/TS config file for basic theming as there was in v3. `DESIGN_SYSTEM.md`'s token system (exact hex values, a `clamp()`-based type scale, a fixed spacing scale, a named easing curve) maps directly onto `@theme` custom properties. Verified against current Tailwind docs before implementation (the original design spec assumed a `tailwind.config.ts` file, which is no longer how the library works).

## D-012 — Placeholder data over a mock Shopify client for pre-commerce UI work

**Decision:** Where the storefront shell needs data that will eventually come from Shopify (navigation categories), use a small, clearly-commented, typed placeholder data file (`lib/navigation-data.ts`) rather than building a mock Shopify Storefront API client.

**Reason:** No Shopify store exists yet, so there's nothing to validate a client interface against — building one now risks guessing wrong about the real API's shape and having to redo it in [ROADMAP.md Phase 2](./ROADMAP.md#phase-2--commerce-foundation). YAGNI per [CLAUDE.md](./CLAUDE.md)'s "do not introduce unnecessary abstractions."

## D-013 — CSS transitions as the starting motion implementation; View Transitions API deferred

**Decision:** Use plain CSS transitions (opacity/visibility) for motion in the storefront shell (menu open/close) before introducing the native View Transitions API or a JS animation library.

**Reason:** Per [DESIGN_SYSTEM.md §62](./DESIGN_SYSTEM.md#62-recommended-frontend-motion-stack)'s layered stack, use the cheapest tier that satisfies the need. The shell's only transition this pass (the full-screen menu) doesn't require spring physics, gesture-driven animation, or orchestrated sequences — a CSS `transition` on `opacity`/`visibility` is sufficient and adds zero bundle weight. The native View Transitions API (`document.startViewTransition`, `view-transition-name`) is not used yet — its value is in animating *between* two rendered views (e.g. a cross-page navigation), and this shell pass only has one real route to transition within. Deferred until a second real page exists to transition to; cross-page shared-element transitions (which would more plausibly need Motion/Framer Motion, or the View Transitions API directly) are deferred for the same reason.

## D-014 — Header utility-nav mobile treatment: icon + visually-hidden text below `md`

**Decision:** Below Tailwind's `md` breakpoint, Header's SEARCH and ACCOUNT utility-nav controls compress from full-text buttons to icon-only presentation (small hand-authored inline SVGs, `aria-hidden`), with the original text preserved as a visually-hidden (`sr-only`) sibling so each control's accessible name is unchanged. MENU and BAG (0) remain full-text at every viewport size.

**Reason:** DESIGN_SYSTEM.md §24's utility-nav specification (`ESQUE MENU SEARCH ACCOUNT BAG (0)`) is explicitly scoped "Desktop" — no mobile treatment was specified, and the as-built Header (Task 8) had none: four full-text buttons in a single non-wrapping row overflowed a 375px viewport (measured 537px scrollWidth), a defect against CLAUDE.md's Fashion Website Priorities, which rank mobile responsiveness above accessibility, performance, reliability, SEO, and security. PROJECT.md §73 requires Bag to "remain immediately accessible" on mobile and establishes MENU's full-screen menu as the primary mobile navigation mechanism — both stay full-text accordingly. SEARCH and ACCOUNT are the two controls without real behavior yet (ROADMAP.md Phase 4/10) and are lower-priority at narrow widths, so they compress. Hand-authored inline SVGs were used rather than adding an icon-library dependency — no icon library exists anywhere else in this codebase, and CLAUDE.md's "avoid unnecessary dependencies" guidance applies; two small icons don't justify a new dependency. Discovered and fixed as an unplanned follow-up task after Task 8's original approval — see the SDD ledger's Ruling 8 for the full discovery/diagnosis trail.

## D-015 — `@shopify/storefront-api-client` + `@shopify/api-codegen-preset` for Storefront API integration

**Decision:** Use `@shopify/storefront-api-client` as the Storefront API client and `@shopify/api-codegen-preset` (with `@graphql-codegen/cli`) to generate TypeScript types from `#graphql`-tagged query documents.

**Reason:** `ARCHITECTURE.md` §2 already ruled out the full Hydrogen framework ("to avoid over-coupling to Shopify's opinionated stack") but left the specific lightweight alternative unnamed. `@shopify/storefront-api-client` is Shopify's own official, framework-agnostic client built for exactly this case — confirmed via Shopify's current documentation, not assumed. Types are generated against Shopify's real Storefront API schema via a public proxy endpoint (`shopify.dev/storefront-graphql-direct-proxy`) that requires no store credentials, so full type safety is achievable before a real store exists — verified directly rather than assumed possible.

## D-016 — Phase 2 narrowed to client + product/collection reads; cart and checkout deferred

**Decision:** This pass of ROADMAP.md Phase 2 implements only the Shopify Storefront API client and typed product/collection read queries. Cart (Storefront API cart object) and Shopify Checkout handoff are deferred to a follow-up phase.

**Reason:** No Shopify store exists yet, so nothing built here can be tested against live data. Read-only product/collection queries can be fully type-verified against Shopify's real, live schema even without a store. Cart mutations and the checkout handoff (which fundamentally means redirecting to a real Shopify-issued checkout URL) cannot be meaningfully verified at all without hitting a live store. The previous phase's final whole-branch review found its two worst defects specifically in code paths that had never been exercised end-to-end (an untested CI pipeline, an unmeasured viewport) — deferring the hardest-to-verify commerce code avoids repeating that pattern on checkout, where the cost of an undiscovered defect is highest.

## D-017 — Commit generated Shopify codegen types (`storefront.generated.d.ts`, `storefront.types.d.ts`); keep the schema cache ignored

**Decision:** `lib/shopify/storefront.generated.d.ts` and `lib/shopify/storefront.types.d.ts` — the two files `pnpm graphql-codegen` produces that TypeScript actually consumes (module augmentation that makes `client.request()` type-safe with no explicit generics) — are now committed to the repository instead of gitignored. `lib/shopify/storefront-*.schema.json` (the codegen-internal schema cache, ~800KB) stays gitignored: it's an intermediate artifact the TypeScript compiler never reads, so committing it has no build-time benefit. No live `pnpm graphql-codegen` step is added to CI.

**Reason:** These two files were originally gitignored under the rationale that they get "the same treatment as `next-env.d.ts`." That analogy doesn't hold: `next-env.d.ts` is regenerated automatically as a side effect of `next dev`/`next build` themselves, so a fresh checkout always has a current copy before TypeScript needs it. `storefront.generated.d.ts`/`storefront.types.d.ts` require a separate, explicit `pnpm graphql-codegen` invocation that nothing in the standard `pnpm install` → `pnpm typecheck`/`pnpm build` pipeline triggers — and `.github/workflows/ci.yml` never ran it either. Verified directly, twice: once pre-fix (5 `TS7031` implicit-`any` errors across `collections.ts`/`products.ts`, exit code 2) and again after this fix wave's other changes landed in those same two files — with both generated files removed and `tsconfig.tsbuildinfo` deleted (to defeat the incremental cache), `pnpm typecheck` still fails the same way (5 `TS7031` errors, exit code 2); restoring the files and clearing the cache again yields a clean pass. Every fresh checkout (CI, Vercel, a new clone) was actually broken, not just theoretically at risk.

Committing ~500KB of deterministic, schema-derived generated code is a better tradeoff than the alternative (adding a live `pnpm graphql-codegen` step to CI/build): that would introduce a network dependency on `shopify.dev`'s public schema proxy at build time, so a transient network failure or upstream outage would break every build, including production deploys — the opposite of what a fix here should do. Keeping builds hermetic (no network calls required to typecheck or build) is worth the generated-file diff noise on regeneration.

Regenerating and re-committing these two files when a query document under `lib/shopify/queries/` changes, or the pinned Storefront API version (`.graphqlrc.ts`, `lib/shopify/client.ts`'s `DEFAULT_API_VERSION`) bumps, is routine maintenance (documented in README.md's Setup section) — it does not need a new DECISIONS.md entry each time. A periodic/manual "codegen drift check" (confirming the committed files still match what `pnpm graphql-codegen` would currently produce) was considered as an optional CI gate; not implemented here, and noted only as a possible future manual/periodic check rather than a build-blocking one, since a drift gate re-run on every CI build would reintroduce the same live network dependency this decision exists to avoid.

## D-018 — Next.js Proxy (not Middleware) for access-gate enforcement

**Decision:** Gate enforcement lives in `proxy.ts` at the repo root, exporting a named `proxy(request: NextRequest)` function, running on the Node.js runtime.

**Reason:** Next.js renamed Middleware to Proxy as of the version this project pins (16.3.1) — confirmed against current Next.js docs, not assumed from training data, which still overwhelmingly reflects the deprecated `middleware.ts`/`export function middleware()` convention. Next.js ships a codemod (`npx @next/codemod@canary middleware-to-proxy .`) for projects migrating off the old convention; this project adopts the current one directly since it never had a `middleware.ts` to migrate from.

## D-019 — `isbot` for crawler detection

**Decision:** Use the `isbot` package (`isBot(userAgentString): boolean`) in `proxy.ts` to let crawlers bypass the access gate unconditionally, rather than a hand-maintained user-agent pattern list.

**Reason:** ARCHITECTURE.md §6 and DECISIONS.md D-005 require the gate to never block crawlers, regardless of cookie state — this is what keeps product/collection routes indexable once they exist (ROADMAP.md Phase 4/5). SEO correctness depends on this list staying current as crawlers change their user-agent strings over time; `isbot` is small, actively maintained (millions of weekly downloads), and purpose-built for exactly this, which a one-off in-house regex would not keep pace with as reliably.

## D-020 — Klaviyo integration via direct REST calls, not the official Node SDK

**Decision:** `lib/klaviyo/client.ts` calls Klaviyo's REST API directly via `fetch` (`POST /api/profile-subscription-bulk-create-jobs/`), rather than adding `@klaviyo/klaviyo-api-node` or an equivalent SDK dependency.

**Reason:** Mirrors the same reasoning already applied to Shopify's lightweight client choice (D-015): this integration needs exactly one endpoint (subscribing a profile to a list with marketing consent), and a single documented REST call doesn't justify a heavier dependency. Verified against Klaviyo's current docs directly — including resolving a real discrepancy mid-implementation between an older, now-superseded flat `subscriptions.email.marketing_newsletter: boolean` shape that some cached references still show, and the current `subscriptions.email.marketing.consent: "SUBSCRIBED"` shape (confirmed across four independent current examples, including Klaviyo's own changelog documenting the shape change). This pass covers only the list-subscription mechanism; the transactional "here's your access password" email (CONTENT.md §4's access-email structure) is not built — like Shopify's store, it needs the project owner's own Klaviyo account and a real email template/flow to exist first, mirroring D-016's reasoning for why cart/checkout were deferred pending a real Shopify store. `first_name` is collected and validated server-side but not forwarded to Klaviyo: the Subscribe Profiles endpoint's documented profile attributes cover identification and consent only, not name — attaching a name would need a separate profile-update call once a real account justifies adding one.

The dated `revision` header (`2026-07-15`) was verified against Klaviyo's current documentation at implementation time and independently re-verified during review, along with the endpoint's trailing slash and the `subscriptions.email.marketing.consent: "SUBSCRIBED"` body shape — an older, now-superseded flat `marketing_newsletter` boolean shape still appears in parts of Klaviyo's own docs corpus and was deliberately avoided. Bump the revision alongside checking Klaviyo's changelog for breaking changes.

## D-021 — Access-gate and Request-Access error copy renders in `--color-esque-text`, not `--color-esque-error`

**Decision:** The access gate's incorrect-password microcopy and the Request Access form's validation errors render in `--color-esque-text`, not `--color-esque-error`. This does not change the palette; `--color-esque-error` remains defined and correct for its other documented uses.

**Reason:** `--color-esque-error` (`#A74338`) measures **3.40:1** against `--color-esque-black` (`#050505`) — computed with the WCAG 2.1 relative-luminance formula, not asserted — which is below WCAG 2.2 AA's 4.5:1 minimum for normal-size text (these are 13px `text-utility` strings). DESIGN_SYSTEM.md's own Error entry independently points the same way: the color "should be used extremely sparingly. Where possible, errors should rely on typography and motion rather than bright red UI" — which is exactly what the gate's shift-and-letter-spacing-split treatment already provides, so nothing is lost by dropping the red. Note explicitly that this is a *different* WCAG criterion from D-010's: D-010 concerned non-text/focus-indicator contrast (1.4.11, 3:1 minimum), this concerns text contrast (1.4.3, 4.5:1 minimum) — which is why it warrants its own entry rather than an amendment to D-010.

## D-022 — AccessForm submits via `useActionState` + uncontrolled input, not a controlled input with a manual handler

**Decision:** `app/(access)/access/AccessForm.tsx` submits via `useActionState` bound to a Server Action through `<form action={formAction}>`, with uncontrolled inputs — matching `RequestAccessForm.tsx` — rather than a React-controlled input driving a manual `onSubmit` handler. The submitted password travels DOM → native `FormData` → `validatePassword`; no React state mediates it. `validatePassword`'s signature is correspondingly `(prevState, formData)`.

**Reason:** The controlled-input pattern (originally specified in this feature's implementation plan) carried a real, user-facing defect. If a keystroke's `input` event fired before React attached its `onChange` listener — observed reproducibly on mobile Safari, and plausible via password-manager autofill on any browser — the DOM held the correctly-typed password while component state stayed `''`, so `validatePassword('')` ran and a *correct* password was rejected with the same branded microcopy a genuine mistake produces. That is a silent lockout on the site's front door, for exactly the early-access audience the gate exists to admit, and Phase 6's entrance motion had just widened the window by adding ~119KB of JS to that route. Reading the value from the form's own `FormData` eliminates the race structurally rather than timing around it, and a Server Action `action` is progressively enhanced by React 19, so a first submission works even before hydration. It also removes two competing patterns for one responsibility in the same directory, which CLAUDE.md prohibits. Record that the fix is pinned by a test that assigns the input's value natively (dispatching no event at all) and asserts access is still granted — a test that fails against the controlled implementation — plus 60/60 passing runs of the formerly-flaky tests at `--repeat-each=20` with no retry wrapper. Note that the incorrect-password microcopy rotation now derives during render from the action result's identity (React's documented "adjust state during render" pattern) rather than from a handler mutation, since `useActionState`'s state is server-returned and has nowhere to track which line was shown last.

**Caveat:** the progressive-enhancement claim above ("a first submission works even before hydration") holds fully for the *correct*-password path, since that redirect is server-side. It does not hold for the *wrong*-password path: `AccessForm.tsx` derives the branded message from `state !== priorState`, and on a server render `priorState` initializes to `state` itself — so a submission that's rejected before hydration has attached re-renders the form with no branded microcopy shown. The action still correctly rejects the password either way; only the branded-message UI is hydration-dependent.

## D-023 — Category pages query Shopify's root `products` connection filtered by product type, not a Collection

**Decision:** Category/subcategory listing pages (`/new`, `/tops`, `/tops/[subcategory]`, etc.) query Shopify's root `products(query, sortKey, reverse, first, after)` connection, with `query` built from `product_type:"..."` search-syntax clauses — never `collection(handle).products`. The category→product-type mapping (`lib/catalog/taxonomy.ts`) is derived directly from `lib/navigation-data.ts`'s existing `NAVIGATION` structure, not a second, parallel taxonomy table.

**Reason:** `ARCHITECTURE.md` §5 and `DECISIONS.md` D-007 require Category and Collection to remain independent dimensions — querying a Collection for a category page would conflate them. The root `products` connection's search-syntax filtering (`field:value`, comparisons, `AND`/`OR`, parentheses) was verified directly against Shopify's current Storefront API docs before implementation, not assumed from memory. Deriving the taxonomy from `NAVIGATION` (already the source Header/FullScreenMenu render from) avoids a second mapping that could silently drift from it.

**Caveat:** this assumes the real Shopify store's `productType` field values will exactly equal `NAVIGATION`'s subcategory labels (`"Hoodies"`, `"T-Shirts"`, …) once a store exists — unverifiable without one. If a real merchandiser uses different strings, the affected category page returns zero results rather than erroring. Mirrors the existing, still-open metafield-namespace caveat in `ARCHITECTURE.md` §5; both should be confirmed together when a real store is provisioned.

**Also recorded here:** Shopify's root `ProductSortKeys` enum has no merchant-curated ordering (`MANUAL`/`COLLECTION_DEFAULT` exist only on `ProductCollectionSortKeys`, which is collection-scoped). "Featured" — `PROJECT.md` §34's default sort option — therefore maps to the root connection's own default ordering rather than true curation. All four of `PROJECT.md` §34's sort options (Featured, Newest, Price Low→High, Price High→Low) are still implemented and selectable, honoring the product spec's exact vocabulary even though "Featured" doesn't yet do more than the API default.

**Implementation note:** the generated `ProductSortKeys` (`lib/shopify/storefront.types.d.ts`) is a real TypeScript string enum, not a string-literal union, and — unlike the other generated types this codebase already consumes — it's only ever `import type`-able here (there is no corresponding runtime `.js` for its enum members to be referenced as values from, confirmed by inspecting the generated file directly, which itself only ever imports it via `import type`). `lib/shopify/products.ts`'s `getProducts()` therefore accepts a plain `'CREATED_AT' | 'PRICE'` literal type on its public options (keeping `lib/catalog/filters.ts` independent of any Shopify-generated type) and casts narrowly at the single point that value crosses into the GraphQL variable, rather than loosening the function's public type or casting more broadly.

## D-024 — Phase 4 filters narrowed to Sort, Availability, and Price range; Size, Color, and Collection deferred

**Decision:** This pass builds Sort (all four `PROJECT.md` §34 options), Availability (in-stock toggle), and Price range (min/max) as zero-JavaScript, URL-driven filters — plain `<Link>`s for Sort, one native GET `<form>` for Availability/Price. Size, Color, and Collection filters are not built. `DESIGN_SYSTEM.md` §51's mobile bottom-sheet filter treatment is also not built this pass.

**Reason:** Size/Color have no real taxonomy yet — `PROJECT.md` §101 still lists product sizes/colors as an open decision, the same category of gap `DECISIONS.md` D-012 already named for navigation data before real Shopify data existed. Building a filter against a guessed size/color enum risks the exact wrong-guess problem D-012 avoided. Collection has only one real member in the current catalog (Collection 001) — a Collection filter has no second collection to prove it actually excludes anything, and intersecting a category's product-type query with a specific collection is a different, untested query shape (`collection(handle).products` vs. root `products(query:)`) not needed by anything else this pass. The mobile bottom-sheet treatment's value is hiding a *large* control set from a small screen; three simple controls (a handful of links, one checkbox, two number fields) don't yet justify that complexity or its JS cost — natural to add once Size/Color/Collection expand the control set later.

**Also recorded here:** Filters were deliberately implemented with zero client components — Sort as plain `<Link>`s (each preserving other active params via `buildFilterHref`), Availability/Price as one native GET `<form>` with no `onChange`/`onSubmit` handler. This works with JavaScript disabled, needs no new client-side bundle weight, and reuses the existing `Button`/`Input` components rather than introducing new form primitives. The availability checkbox tints its checked state via Tailwind's `accent-color` utility (`accent-esque-forest`) rather than a custom-built widget — a sparing, genuine use of the forest accent for a real selection state per `DESIGN_SYSTEM.md` §5, on a native control whose own contrast/rendering is otherwise governed by the browser, not hand-drawn CSS (unlike D-010's focus-ring case, where the author was fully responsible for the visual). Worth a second look once a real UI/accessibility review pass exists to check rendered contrast across engines.

## D-025 — Predictive full-screen search (ROADMAP.md Phase 4) deferred in full

**Decision:** No search functionality — predictive or otherwise — is built this pass. Header's `SEARCH` control remains the no-op it already was.

**Reason:** Unlike a category grid, whose correctness is fully specified by "does it show the right products for this category" (verifiable with a handful of fixtures, exactly as `getProducts` is tested), predictive search's entire value proposition — relevance/ranking quality against a real catalog, `PROJECT.md` §33's "feels instantaneous" — is fundamentally about live-store interaction. ## D-026 — Unknown-subcategory 404s return HTTP 200 + `noindex`, not a hard 404; not resolved this pass

**Decision:** `/tops/[subcategory]`, `/bottoms/[subcategory]`, and `/etc/[subcategory]` correctly render the branded `THIS PIECE DOESN'T EXIST.` UI for an unrecognized subcategory slug (verified via Playwright and manual production testing), and Next.js correctly injects a `noindex` meta tag on that response (verified in the rendered HTML) — but the HTTP response status is `200`, not `404`. This is recorded as a known, investigated, but unresolved limitation, deferred to ROADMAP.md Phase 12's SEO pass rather than fixed here.

**Investigation:** Discovered during this phase's final validation pass via a manual `next start` (production build) `curl` check — Playwright's E2E suite runs against `next dev` and only asserts rendered content/headings, never the raw HTTP status code, so it could not have caught this. Root-caused directly against Next.js's current documentation (`docs/01-app/03-api-reference/04-functions/not-found.mdx`, `docs/01-app/02-guides/streaming.mdx`): "a `not-found` boundary... will return a `200` HTTP status code for streamed responses, and `404` for non-streamed responses," and calling `notFound()` "after streaming has started... returns a 200 status code instead of a 404. To return a real 404 status, the resource must be checked before the response begins streaming." Three independent, evidence-based fix attempts were made and empirically disproven, each verified with a real `next start` + `curl` round-trip (not just re-reading the docs and assuming):
1. **Moving the `notFound()` check earlier** — synchronously in each `[subcategory]/page.tsx`, before rendering `<CategoryListing>` at all (still landed in this pass — see the code comments in those files — because it independently avoids an unnecessary Shopify call for a request already known to be invalid, which is worth keeping regardless). Confirmed via server logs that this successfully prevents the Shopify call, but the response status was still `200`.
2. **A segment-local `not-found.tsx`** under `app/(storefront)/tops/[subcategory]/`, on the theory that the distance to the nearest not-found boundary (this app only had a root-level one) was forcing an early flush. Still `200`.
3. **`generateStaticParams()` + `dynamicParams = false`**, enumerating the known-valid subcategory slugs so an unrecognized one would fail to match the route at all (the same bucket a truly unmatched URL like `/this-route-does-not-exist` already falls into, which *does* correctly return a hard `404` — confirmed directly). Build succeeded without attempting a build-time Shopify call (an important safety check, since that would have broken `pnpm build`), and the known-valid subcategories still rendered correctly, but an unrecognized slug still returned `200`.

A fourth, isolated reproduction — a single-line, `force-dynamic` page at the app root (`app/test-notfound-probe/`, no route group, no shell, no ancestor Client Component, calling `notFound()` as its only statement) — **also** returned `200`. This rules out this project's specific shell architecture (`(storefront)/layout.tsx` wrapping every page in the Client Component `ShellClient`) as the cause: the behavior reproduces in the barest possible case, so it appears to be this Next.js version's general treatment of `notFound()` in a dynamically-rendered (non-statically-prerenderable) route, not something specific to Esque's code. All temporary probe files were removed; nothing from the investigation itself is committed.

**Reason for deferring rather than continuing to iterate:** The practical SEO risk is meaningfully mitigated already — Next.js's own `noindex` tag is confirmed present and active, which is the framework's documented, intentional safety net for exactly this case, so a mistyped subcategory URL will not get indexed even without a hard 404. A fully correct fix likely requires either a deeper investigation than a reasonable stopping point within a catalog-focused pass allows (e.g., checking Next.js's issue tracker for this exact version/Turbopack combination, or testing configuration combinations beyond the three above), or a decision to serve these seven routes differently (e.g., fully static generation for the known-valid subcategories with `notFound()` reserved only for a route that genuinely doesn't exist in the file system — which would need its own careful design, not a bolt-on). ROADMAP.md Phase 12 ("SEO pass... crawlability") already owns exactly this class of problem holistically and is the right place to resolve it properly, rather than a partial fix here that might need to be redone.

## D-031 — Recently Viewed: versioned `localStorage`, read via `useSyncExternalStore`

**Decision:** `lib/product/recently-viewed.ts` holds pure, storage-agnostic logic (`readRecentlyViewed`/`recordRecentlyViewed` against a minimal injected `{getItem, setItem}` interface, not DOM lib's full `Storage`) — versioned (`{v: 1, items: [...]}`), capped at 8, deduped by handle (most-recently-viewed moves to the front), and never throws on a full/blocked/corrupt store. `components/product/RecentlyViewed.tsx` reads the list via `useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot)` — `getServerSnapshot` returns `[]` so SSR and the first client render agree, `subscribe` listens for the native `storage` event (cross-tab updates only — same-tab writes never fire it, by Web Storage API design), and `getSnapshot` caches its parsed result by content (comparing the raw JSON) so repeated calls return a referentially-stable array when nothing has changed. Recording the current product into storage stays a separate, plain `useEffect` that never calls a React state setter itself.

**Reason:** The original plan for this component (see `docs/superpowers/plans/2026-09-05-pdp-implementation.md` Task 8) called a state setter (`setItems(...)`) synchronously inside the same effect that performed the `localStorage` write. `eslint-plugin-react-hooks@7.1.1` (installed transitively via `eslint-config-next@16.3.1`, confirmed directly in `node_modules`) ships `react-hooks/set-state-in-effect` at `"error"` in the recommended config this project extends (`eslint-config-next/core-web-vitals`) — an effect whose job is mirroring an external store into React state via `setState` is exactly the shape `useSyncExternalStore` exists to replace, and this project's actual, current lint configuration enforces that rather than merely suggesting it. Separately, and independent of lint: reading `localStorage` directly during render (no hook at all) would have caused a genuine hydration mismatch (`window`/`localStorage` exist from the client's very first render, before any effect runs, so a plain synchronous read would disagree with the server's necessarily-empty render) — `useSyncExternalStore`'s `getServerSnapshot` parameter is the documented, correct fix for precisely that failure mode, not something either alternative (the original plan, or a naive direct read) handled correctly on its own. The module-level snapshot cache is safe here specifically because this file is `'use client'`-only (confirmed by its own directive) — it never executes on the server, so it carries none of the cross-request-leakage risk `server-no-shared-module-state` warns about for RSC/SSR code; it is scoped to one browser tab's one loaded copy of the module.

**Also recorded here:** every prop `RecentlyViewed` takes is a primitive (`handle`, `title`, `imageUrl`, `imageAlt`, `priceAmount`, `priceCurrency`), not a nested object — deliberately, so the recording effect's dependency array can be fully exhaustive with no `eslint-disable` needed (each dependency is a primitive the effect actually reads), per the same "primitive effect dependencies" principle the vercel-react-best-practices skill documents.

## D-035 — Hotspot hit-regions are real `<button>`s with percentage-based `clip-path`, not SVG-path-as-ARIA-button or an ARIA tablist; click toggles the info panel rather than navigating; Shop the Look is the accessible alternative to the silhouette map

**Decision:** Each hotspot in `SilhouetteIllustration.tsx` is a real, native `<button>` element, absolutely positioned over the placeholder illustration and shaped via `clip-path: polygon(...)` expressed entirely in **percentage** units (both the button's own `top`/`left`/`width`/`height` box and the polygon's vertices within that box). Two alternatives were considered and rejected:

- **An SVG `<path>` given `role="button"`, `tabIndex`, and manual `keydown` handling.** This would need hand-written Enter/Space activation (including an easy-to-miss `preventDefault()` on Space to stop page scroll) that a real `<button>` provides natively for free — the same "prefer native semantics over hand-rolled ARIA" reasoning D-027 already established for the PDP's size/color selector.
- **An ARIA `tablist`/`tab`/`tabpanel` pattern** (arguably the "most correct" ARIA widget for "exactly one of several regions is selected at a time"). Rejected as more complexity than two mutually-exclusive toggle regions warrant — a roving-tabindex implementation is a well-known source of subtle accessibility bugs, and PROJECT.md/DESIGN_SYSTEM.md never describe this interaction as tab-like browsing (arrow-key-driven) rather than direct point-and-activate.

Percentage-based `clip-path: polygon()` (not CSS `clip-path: path()`, and not an SVG `<path>`'s own coordinate space combined with a separately-positioned HTML hit-region) was chosen specifically because percentages resolve against the element's own box at every reflow, natively, with no JavaScript: the visible shape and the actual pointer/touch hit-region (`clip-path` constrains hit-testing, not just paint, in every evergreen browser — confirmed directly during manual verification, not just asserted: a click at the exact center of the "Bottom" hotspot's bounding box, which falls in the deliberate gap between the two legs, correctly passes through to the element behind it) can never drift apart at any viewport width. A `clip-path: path()` or a separate SVG viewBox coordinate system would each need a `ResizeObserver` recomputing raw pixel coordinates to stay aligned on resize — real, avoidable fragility for a responsively-scaled illustration.

Clicking (or pressing Enter/Space on, or tapping) a hotspot **toggles** the info panel open/closed for that garment; it does not navigate to the PDP. PROJECT.md §28 describes clicking a garment as a *shared visual transition* into the PDP — an animation ROADMAP.md Phase 9 owns explicitly ("Shared-element product transitions (grid → PDP, interactive model → PDP)"). Shipping a hard navigate-on-click now would be easy to trigger by accident while exploring an invisible-until-labeled, irregularly-shaped hit region, and would need rewiring the moment Phase 9 adds the real transition. The panel's own explicit `VIEW PRODUCT` link (CONTENT.md §10's canonical CTA) is the one real navigation trigger, identical for desktop, keyboard, and touch — a single interaction model rather than a hover-capability-detected branch, per PROJECT.md §94's "familiar fundamentals" principle. Hover and focus both preview a region (mouse/keyboard parity); deliberately no `onMouseLeave`/`onBlur` handler exists, so the panel never auto-closes when the pointer/focus leaves a hotspot — verified this avoids a real hover-to-panel race (moving the mouse from the hotspot toward the panel's own controls) rather than merely being asserted safe.

The always-visible `SHOP THE LOOK` control is the deliberate, real answer to this task's own flagged accessibility risk — a screen-reader/non-visual alternative to a purely visual silhouette map. Rather than adding a second, `sr-only` text list that duplicates the hotspots' information and could silently drift out of sync with them, `SHOP THE LOOK` opens a panel exposing every garment as independent, fully keyboard-and-screen-reader-operable controls (name, price, variant selection), reachable without ever perceiving or interacting with the illustration at all.

**Reason:** This task named the silhouette-map accessibility gap explicitly as "a real accessibility risk worth designing around explicitly, not an afterthought" — the resolution above is a first-class design decision, not a bolted-on `sr-only` patch. The click-vs-navigate reconciliation avoids literally implementing a half-built version of an animation a later, already-named phase owns, consistent with D-032's reasoning for not partially building Phase 9's parallax inside Phase 7.

## D-036 — `VariantPicker` extracted from `ProductPurchasePanel` for a third call site; requires a `namePrefix` the single-consumer PDP usage never needed

**Decision:** The PDP's existing per-option radio-group markup (D-027: `sr-only peer` input + a sibling `<label>` styled via `peer-checked`/`peer-disabled`/`peer-focus-visible`) is extracted from `ProductPurchasePanel.tsx` into `components/product/VariantPicker.tsx`, now shared by three call sites: the PDP, the Interactive Model's per-garment info panel, and Shop the Look's per-item rows. `ProductPurchasePanel` is otherwise behaviorally unchanged — same markup, same styling, same logic, just relocated. Its private `formatPrice` helper is similarly extracted to `lib/product/price.ts` for the same three-call-site reuse.

`VariantPicker` takes a new required `namePrefix: string` prop, built as a call-site tag plus the garment's Shopify handle (`pdp-${handle}` on the PDP, `preview-${handle}` in the Interactive Model's hover panel, `look-${handle}` per Shop the Look row) — used to build each radio input's native `name` and `id` attributes. Native radio-group scoping is by `name` value document-wide, absent a `<form>` boundary, and this holds even for a radio inside a *closed* native `<dialog>` — its content remains part of the document regardless of visibility. The PDP only ever mounts one `VariantPicker` at a time, so this never surfaced; Shop the Look mounts one per included garment simultaneously (and can be mounted alongside the hover panel's own `VariantPicker` for the same garment), and two garments both having a "Size" option (T-shirt sizes and pants sizes are both typically named "Size" in Shopify) would otherwise render two `<input name="Size">` groups that the browser treats as one shared, mutually-exclusive group — selecting a size for one garment would silently un-check the other's. The call-site tag (not just the handle) additionally prevents the same garment's own two simultaneously-mounted pickers (hover panel + Shop the Look row) from colliding with each other.

**Reason:** CLAUDE.md's "avoid introducing competing patterns for the same responsibility" — the alternative was hand-rolling this same accessibility-load-bearing markup a second and third time, risking three copies independently drifting out of sync with D-027's ruling (e.g., a future focus-ring color change would need to be found and fixed in three places instead of one). The extraction is a pure, behavior-preserving refactor of an already-shipped file, scoped as its own task/commit specifically so it's reviewable in isolation from the new Phase 8 feature code it exists to serve. The `namePrefix` collision was identified by reasoning through the DOM's radio-grouping rules during design, before implementation — not discovered as a bug afterward.

## D-037 — Independent review found a real keyboard-accessibility failure in the Interactive Model; corrects D-035's "hover and focus both preview" description and closes a Shop the Look sold-out gap

**Decision:** Before Phase 8 was considered complete, an independent `ui-reviewer` pass (not the implementer) reviewed the shipped Interactive Model against DESIGN_SYSTEM.md/the design spec and reproduced a genuine defect live in a browser (via the same fixture-stub manual-verification technique D-034 used), not just by reading the code. Per this project's "don't rewrite history" convention, D-035's original text is left as written; this entry corrects what it described and records the fix, rather than editing D-035 in place.

**Finding — keyboard-unreachable panel (accessibility-blocking, confirmed).** D-035 as originally written had both hotspot `<button>`s call `onHover` from `onFocus` as well as `onMouseEnter`, intending "mouse and keyboard parity." Both hotspot buttons sit in DOM order before the single shared info panel (`InteractiveModelExperience.tsx`). Because merely *focusing* a button also reassigned `activeRegion`, sequentially tabbing from the first hotspot to the second silently replaced the panel's content before a keyboard user could ever tab forward into the first garment's own `VIEW PRODUCT`/`QUICK ADD`/size controls — with two regions, the first region's panel controls were **permanently unreachable by keyboard**, a confirmed WCAG 2.1.1 (Keyboard) failure for exactly the interactions Stage 2/3 claim are done. Mouse and touch users were unaffected (a click/tap goes directly to the visible panel without depending on sequential tab order).

**Fix:** `onFocus` no longer calls `onHover` — mouse hover still previews a region (`onMouseEnter`, unchanged), but a keyboard user must explicitly press Enter/Space (which fires the existing `onClick`/`handleToggle`, exactly like a click) to activate a region. Merely tabbing past a hotspot now never changes what the panel shows, so the panel a keyboard user reaches via subsequent Tab presses is always the one they deliberately activated — verified by live reproduction after the fix: focusing "Top" alone leaves the neutral prompt showing; pressing Enter shows Hoodie 01's panel; tabbing six more times (through Hoodie 01's own size control, `VIEW PRODUCT`, `QUICK ADD`, past the "Bottom" hotspot, and beyond) leaves Hoodie 01's panel shown the entire time, confirming its controls are now genuinely reachable. This is a corrected description of D-035's interaction model, not a reversal of its other conclusions — native `<button>`s, percentage `clip-path`, click-toggles-rather-than-navigates, and `SHOP THE LOOK` as the non-visual alternative all stand exactly as D-035 described them.

**Finding — Shop the Look never applied the sold-out treatment (spec-compliance gap, confirmed).** The design spec's own Error/Empty States section already specified that a sold-out garment in Shop the Look must show `NO LONGER AVAILABLE.` in place of its variant picker and can never count toward a valid `ADD LOOK`; the shipped `ShopTheLookPanel.tsx` did neither — it rendered a full grid of disabled, struck-through sizes with no explanation, and `isLookAddValid`'s completeness check had no availability check at all, so a sold-out product whose only option auto-completes (any single-value, non-"Size" option — `getInitialSelections`) could pass validity despite being entirely unavailable.

**Fix:** `initialSelectionMap` now initializes a sold-out garment (`isProductSoldOut`) as `included: false`, and its checkbox is rendered `disabled` — so it can never become included by user action, closing the gating gap without changing `isLookAddValid`'s signature (it already only evaluates included items). The sold-out branch renders `NO LONGER AVAILABLE.` instead of `VariantPicker`, matching the PDP and the Interactive Model's own info panel exactly. Verified live: a fully sold-out fixture item shows the correct copy, its checkbox is disabled and unchecked, and `ADD LOOK` correctly becomes valid based on the other, available item alone.

**Two smaller corrections from the same review, applied directly (not separately decided):**
- Shop the Look's checkbox now has an explicit `aria-label={"Include " + title}` (the design spec already specified this; the shipped version relied on the wrapping `<label>`'s implicit, much longer, multi-line computed name instead). `aria-label` takes precedence over that computed name, so the `<label>` wrapper is kept for its larger click target.
- `SilhouetteIllustration`'s dimmed-region opacity moved from `/25` to `/40`, inside DESIGN_SYSTEM.md §29's documented 35-50% range (the original value was a plain numeric slip against an explicit spec value, not a judgment call).
- `ShopTheLookPanel`'s `ADD LOOK` now shows a disabled-reason hint ("Select at least one piece to continue." / "Select all options to continue."), matching the equivalent hint already present on the PDP and the Interactive Model's own info panel.

**Considered and not changed:** the review also noted `aria-pressed` reflects hover/focus preview rather than strictly a "press." Removing focus from the preview path (above) already closes this for keyboard/screen-reader users — the primary audience `aria-pressed` serves — since it now only changes via an actual Enter/Space/click activation for them; a sighted mouse user's hover still sets it early, which was judged an acceptable, minor residual gap rather than one requiring its own architectural change, since mouse users are not the audience listening to `aria-pressed` announcements.

**Reason:** This models the completion standard CLAUDE.md and this project's engineering-lead workflow actually require — dispatching an independent reviewer for a novel, accessibility-sensitive interaction pattern before declaring it done, and treating that reviewer's *live-reproduced* findings (not merely code-read opinions) as load-bearing rather than advisory. Recording the finding, the fix, and the verification evidence here — rather than quietly editing the code and leaving D-035 to read as if it had always been correct — keeps this file's ADR purpose intact: a durable, honest record of what was decided, what was wrong, and why the correction is trustworthy.

## D-038 — Shared-element product transitions use React's `<ViewTransition>` (native browser View Transitions API); resolves D-013's deferral

**Decision:** Cross-page shared-element transitions (grid → PDP, Interactive Model → PDP) are implemented with React's `<ViewTransition name=... share="morph" default="none">`, imported from `'react'`, backed by the browser's native View Transitions API. No new npm dependency — `motion` (already installed per D-006) is deliberately not used for this.

**Mechanism verification, done before committing to this rather than assumed:** this project pins `react`/`react-dom` 19.2.8 (stable) and `next` 16.3.1. `ViewTransition` is not exported from the stable `react` package's runtime, nor declared in `@types/react`'s default `index.d.ts` (confirmed by direct grep of both). Next.js 16.3.1 ships its own bundled documentation (`node_modules/next/dist/docs/01-app/02-guides/view-transitions.md`) stating plainly that "View transitions work in the App Router with no configuration. The App Router uses React canary releases, which contain all stable React 19 changes as well as newer features like `ViewTransition`" — corroborated by `node_modules/next/dist/compiled/react-experimental/` existing as a real, shipped build Next's own bundler substitutes for App Router code. No `experimental.viewTransition` config flag exists in this version's `NextConfig` type or runtime config schema (confirmed by grep) — consistent with "no configuration needed." The `vercel-react-view-transitions` skill's mention of that flag is stale relative to this exact pinned version; the version-matched bundled doc was treated as authoritative.

**Type activation — a triple-slash reference, not `import {} from 'react/experimental'`:** `ViewTransition`'s types live only in `@types/react`'s `experimental.d.ts`/`canary.d.ts`. A global tsconfig `"types"` array was considered and rejected (TypeScript's documented behavior: setting `"types"` explicitly stops auto-including every other `@types/*` package, e.g. `@types/node`, silently breaking unrelated typechecking). `import {} from 'react/experimental'` was tried next and also rejected — empirically, not just by reasoning about it: it typechecks, but compiles to a real, literal side-effect import (TypeScript does not elide a bare, non-`type`-qualified import just because it has zero named bindings), and Next's Turbopack bundler then fails `pnpm build` with "Module not found: Can't resolve 'react/experimental'" — `react`'s own `package.json` `exports` map has no `./experimental` entry; it isn't a real module, only a virtual path for the type declarations. A `/// <reference types="react/experimental" />` triple-slash directive is what's actually used, once per file that imports `ViewTransition` (`ProductCard.tsx`, `ProductGallery.tsx`, `SilhouetteIllustration.tsx`) — a pure compiler directive, stripped unconditionally by every tool (tsc, SWC, Babel), never emitted as code.

**What gets wrapped — the container, not the `<Image>` conditionally:** `ProductCard`'s and `ProductGallery`'s existing image-container `<div>`s (which render unconditionally regardless of whether a real photo exists) are wrapped whole, keyed by `lib/product/view-transition.ts`'s `getProductViewTransitionName(handle)` — a single source of truth so every pairing agrees byte-for-byte, with defensive sanitization of the handle (Shopify's handle format is not contractually guaranteed CSS-`<custom-ident>`-safe; PROJECT.md §101 lists product data as still open). This gives an honest, functioning shared-element target today, before real photography exists (PROJECT.md §101) — a plain color block growing from grid-cell to PDP-hero size/position — that will automatically look richer once real photography lands, with no further code change.

**`ProductCard`'s `enableSharedTransition` prop defaults to `false`:** a concrete, non-speculative naming collision was identified during design. The homepage renders both `SelectedPieces` (up to 3 products via `getSelectedPieces()`) and the Interactive Model (2 products via `getInteractiveModelLook()`) as two independent Shopify queries against the same 6-product Collection 001 catalog — both can realistically resolve to the same product (e.g. Selected Pieces' unscoped "first N products" query and the Interactive Model's "first product of type Tops" query can trivially name the same hoodie). Two simultaneously-mounted elements sharing one `view-transition-name` is a real failure mode, not just cosmetic — confirmed directly: React logs "There are two `<ViewTransition name=...>` components with the same name mounted at the same time. This is not supported and will cause View Transitions to error," reproduced live via a temporary fixture-backed scratch route that deliberately co-mounted two components carrying the same name (removed before commit). Rather than trying to guarantee two independent, unrelated Shopify queries can never overlap, `ProductCard` defaults the feature off; `ProductGrid` (its only other consumer — category pages and the PDP's own Related Products, both single-query, no-duplicate-handle, never co-rendered with the Interactive Model) passes `enableSharedTransition` through unconditionally. `SelectedPieces` needs no code change — it simply doesn't opt in, and still navigates normally with no morph (full graceful degradation).

**Styling and the reduced-motion gap:** `share="morph"` + `default="none"` per React's documented pattern, styled via a CSS recipe adapted from the `vercel-react-view-transitions` skill's documented pattern (blur-during-morph to hide pixel-interpolation artifacts, `::view-transition { pointer-events: none }` so mid-transition clicks aren't lost) but re-expressed in Esque's own Editorial-tier timing (DESIGN_SYSTEM §21: 500-800ms) and `--ease-esque`, not the demo's own arbitrary values. The sitewide universal-selector `prefers-reduced-motion` rule (`app/globals.css`) does not reach the browser's UA-generated `::view-transition-*` pseudo-element tree — confirmed against Next.js's own bundled View Transitions guide, which documents this exact gap and ships its own targeted recipe rather than relying on a universal selector. A dedicated rule targeting `::view-transition-old(*)`/`::view-transition-new(*)`/`::view-transition-group(*)` was added, and is verified deterministically in `tests/e2e/reduced-motion-audit.spec.ts` by parsing the actual computed stylesheet rule rather than depending on a live, timing-sensitive transition.

**Scope, deliberately narrow:** only the shared-element morph pattern is built — no sitewide directional page-transition system (`transitionTypes`/`nav-forward`/`nav-back`, confirmed available on `next/link` at this Next version but unused). The task named "shared-element product transitions," not a sitewide slide system, and building the latter would mean auditing and instrumenting every navigation in the app, a materially larger commitment.

**Honest limitation:** this dev/CI environment has no configured Shopify store (every product/category route hits the generic error boundary — see `catalog.spec.ts`/`pdp.spec.ts`). A shared-element pair can only form when the destination content renders in the same navigation commit; an unconfigured store means the PDP route never currently renders real content to pair against. The mechanism is real and correct regardless (verified directly: clicking a fixture `ProductCard`/hotspot navigates correctly, console-clean, and the existing `catalog.spec.ts`/`pdp.spec.ts`/`homepage.spec.ts` suites all pass unmodified) — its visual payoff is only fully realized once a real, reasonably fast-responding Shopify store exists.

**Reason:** D-006/ARCHITECTURE.md's motion stack already names "View Transitions where appropriate" ahead of Motion's layout animations for exactly this class of problem; D-013 explicitly deferred adopting it "until a second real page exists to transition to," which is now true many times over (catalog grid, PDP, homepage, Interactive Model). Browser-support graceful degradation ("without browser support, your application works normally; the transitions do not animate," per Next's own bundled guide) satisfies INTERACTIONS.md §10's "must degrade gracefully and must never prevent navigation" as a platform guarantee rather than something hand-built.

## D-040 — Custom cursor: desktop-only, vanilla React/DOM (no `motion` dependency), scoped to the storefront shell only

**Decision:** `components/navigation/CustomCursor.tsx` implements DESIGN_SYSTEM §22-23/INTERACTIONS §7's custom cursor with plain `useRef`/`useEffect` and native DOM APIs — no animation library. It renders nothing at all, leaving the OS cursor completely untouched, unless every one of: a fine, hover-capable pointer (`(hover: hover) and (pointer: fine)` — a single check that excludes touch and hybrid/coarse pointers together), motion is not reduced, and the device doesn't report an obviously low-power profile (`lib/motion/media.ts`'s `isLowPerformanceDevice`: `hardwareConcurrency <= 2` or `deviceMemory <= 2`, a deliberately conservative, best-effort heuristic — a false negative on an actually-weak device is the accepted failure mode, not a false positive on ordinary mid-range hardware). Even when eligible, the OS cursor is never hidden (no `cursor: none` class applied) until a real `pointermove` has actually been observed — an `initialized` flag that flips exactly once, only inside the real event handler, per DESIGN_SYSTEM §23's explicit rule.

Position is written directly to the DOM (`ref.current.style.transform`) inside the native `pointermove` handler, never through React state, so there is no re-render — and no synthetic interpolation lag — on the high-frequency hot path (DESIGN_SYSTEM §22: "If the cursor feels delayed, disable interpolation" — this implementation has none to disable). Label and form-field-hidden state only call `setState` when the computed value actually changes (tracked via refs), so re-renders happen only on meaningful transitions, never per pixel of movement.

Contextual labels use a generic, opt-in `data-cursor="LABEL"` attribute read via one delegated `pointermove` listener (`event.target.closest('[data-cursor]')`) rather than per-element handlers. Only two call sites are wired, both textually grounded in explicit DESIGN_SYSTEM lines rather than invented: `data-cursor="VIEW"` on `ProductCard`'s link (§39: "cursor becomes VIEW") and `data-cursor="OPEN"` on `FullScreenMenu`'s category links (§25: "custom cursor changes to OPEN"). `SHOP`/`DRAG`/`NEXT` remain supported by the component's API for a future call site that actually needs them.

The cursor is mounted once in `ShellClient` (the storefront shell) and deliberately **not** on `/access` — the access gate keeps its own existing, already-shipped, already-reduced-motion-correct `EntranceMotion` pointer treatment (PROJECT.md §13's "interactive cursor effects" requirement is already satisfied there); layering a second, generic follow-cursor on top of that one-time atmospheric sequence would compete with it visually on the site's single most important first impression.

**Reason:** No `motion` dependency because the feature's own spec explicitly wants *zero* interpolation lag, which vanilla direct-DOM-write handles more simply and cheaply than a spring/animation library would — consistent with D-006's layered stack (use the cheapest tier that satisfies the need). Verified live (initialization-safety under rapid navigation and menu-opening before any pointer movement, reduced-motion, touch-project gating, form-field hiding, contextual labels, and that adding `data-cursor` introduces no new DOM node/`tabIndex` and doesn't disturb existing focus order) by both the dedicated `tests/e2e/custom-cursor.spec.ts` suite and an independent review pass, which found no defects in this component.

## D-041 — Homepage parallax scoped to Scene 01 (Hero) only; vanilla CSS-custom-property mechanism, no `motion` dependency

**Decision:** Picks up D-032's deferral of Hero's cursor-driven depth (DESIGN_SYSTEM §27). `components/home/HeroParallax.tsx` is a thin `'use client'` wrapper (`display: contents` — zero layout-box impact, so it cannot disturb `CollectionHero`'s existing flex/absolute positioning relationships) around Hero's three existing, still server-rendered layers. Each layer carries its own `--depth` (0.3/0.6/1.0, mirroring `EntranceMotion`'s existing three-tier convention) and a shared `.esque-parallax-layer` CSS class that reads both properties via `calc()`. Gated by the same `lib/motion/media.ts` checks as the cursor (reduced motion, fine-pointer-and-hover — a touch device has no cursor to track, and DESIGN_SYSTEM §59/INTERACTIONS §16 both call for reducing pointer-dependent depth effects on mobile), plus a CSS-level `prefers-reduced-motion` backstop forcing `transform: none` as defense in depth.

Scene 04 (Selected Pieces) is a functional product grid with no spec basis for parallax and a real cost to drifting navigational product imagery under the cursor. Scene 05 (Categories) has only a discrete, spec'd *hover* typography shift (§34) — a smaller, different, already-covered concern (general hover philosophy, §18) — not continuous cursor-tracked depth, and no real category imagery exists yet to create depth against.

**Reason (why not `motion`, unlike `EntranceMotion`):** ROADMAP.md's own Phase 12 note already flags `EntranceMotion`'s ~119KB decoded JS as an unresolved cost on the `/access` route. Loading `motion` a second time on `/` — the site's most-trafficked, LCP-critical route — to reproduce an effect this simple (translate two or three layers a few px based on pointer position) would repeat that exact mistake on a more important route, which this phase was explicitly asked not to do "uncritically." `CollectionHero`'s own existing entrance fade (`.esque-hero-reveal`) already established the precedent of plain CSS for this scene rather than a library; the new parallax work extends that same pattern rather than introducing a second, heavier one for the same file. `EntranceMotion` itself is left untouched — its own animation needs (a synchronized scale/opacity entrance together with parallax) are more complex, and refactoring already-shipped, tested code is outside this phase's audit-only mandate over prior work.

Verified live by both `tests/e2e/homepage.spec.ts`'s dedicated "hero parallax" suite and an independent review pass: realistic mouse movement (roughly a quarter of the viewport from center) produces a genuinely subtle ~3-4px shift on the nearest layer; the mathematical ceiling at the extreme viewport edge is 24px × 14px, a little past a strict reading of "a few pixels" but still restrained and not distracting — recorded here as a considered, accepted judgment call against the design system's own non-numeric wording, not a defect.

## D-043 — Interactive Model: a mouse click could never open the info panel; corrects D-035's "clicking toggles the panel" description

**Decision:** An independent review (mirroring D-037's own established process on this exact feature) live-reproduced a real defect in `InteractiveModelExperience.tsx`'s hotspot click handling, in a file this phase's shared-element transition work (D-039) touched and asserted was reverified. `handleToggle` (`setActiveRegion((prev) => (prev === region ? null : region))`) was reachable in practice only through a browser's real event order: `mouseenter` always fires before `click` for any click on an element the pointer wasn't already resting on, so `onHover` had already set `activeRegion` to the clicked region by the time `onClick` ran — `prev === region` was therefore always `true` at click time, and the toggle could only ever collapse to `null`. Confirmed live, three ways: hovering a hotspot then clicking that same, now-active hotspot closed its panel every time; clicking a solid point of a different hotspot (bypassing the deliberate D-035-documented pass-through gap at its bounding-box center) after first hovering the other one also only ever closed rather than opened. A mouse user — the majority desktop input method — could never use a click to *open* a panel; every click on every hotspot closed whatever hover had already shown, directly contradicting D-035's own stated model ("Clicking … **toggles** the info panel open/closed") and this phase's own D-039, which asserted the interaction model was reverified and unchanged.

**Fix:** `handleToggle` is renamed `handleActivate` and now unconditionally sets `activeRegion` to the region rather than toggling it. For mouse users, hover already shows the panel; a click on the same, already-hovered region is now a harmless no-op instead of an unwanted close, and a click on a different hotspot (mouse necessarily enters it first) correctly shows that garment. Keyboard users are unaffected — D-037's own keyboard verification (focus alone must not preview; tabbing past a hotspot must not silently replace the panel; Enter/Space must explicitly activate) never depended on the toggle-to-`null` branch, and was re-verified live after this fix landed: focusing a hotspot still shows nothing new, tabbing onward still doesn't silently replace an already-active panel, and Enter/Space still explicitly activates the focused hotspot exactly as before. `SilhouetteIllustration`'s `onToggle` prop is renamed `onActivate` to match, so the (now-corrected) name no longer implies toggle semantics that don't exist.

## D-047 — `EntranceMotion` replaces `motion/react`'s `useReducedMotion()` with a local, SSR-safe `useSyncExternalStore` hook; resolves the hydration-mismatch warning D-044 flagged and deferred

**Decision:** `app/(access)/access/EntranceMotion.tsx` no longer imports `useReducedMotion` from `motion/react`. In its place, a local hook built on React's `useSyncExternalStore` — `subscribeToReducedMotionChange`/`getReducedMotionSnapshot`/`getReducedMotionServerSnapshot`, the same three-function shape `components/product/RecentlyViewed.tsx` already established for this exact class of problem (DECISIONS.md D-031) — reads `prefers-reduced-motion` via `lib/motion/media.ts`'s already-tested `prefersReducedMotion(matchMedia)` pure function (the same one `CustomCursor.tsx`/`HeroParallax.tsx` already call), rather than duplicating the media-query string a third time. `getServerSnapshot` returns `false`, matching what the component's ternaries (`prefersReducedMotion ? … : …`, now `shouldReduceMotion ? … : …`) already treat as the default. `SilhouetteLayer`'s `prefersReducedMotion` prop is renamed `shouldReduceMotion` and its type narrows from `boolean | null` to `boolean` — the tri-state was only ever a side effect of `motion/react`'s hook, not a real third state this component ever needed.

**Root cause, confirmed live before fixing (not just read from the code):** `motion/react`'s `useReducedMotion()` (`framer-motion/dist/es/utils/reduced-motion/use-reduced-motion.mjs`) resolves its value from a module-level ref (`motion-dom`'s `prefersReducedMotion.current`) that a lazy `initPrefersReducedMotion()` call computes **synchronously during render** — not inside an effect — the first time the hook runs anywhere in the app's lifetime on a given environment. On the server, `window` doesn't exist, so this ref is left at its initial value, `null`, for the whole SSR pass. On the **client's very first render — during hydration itself** — `window.matchMedia('(prefers-reduced-motion)').matches` is read immediately, synchronously, before React finishes reconciling against the server HTML. For a visitor whose OS already has reduced motion enabled, this means the client's hydration-time render already evaluates the hook as `true`, while the server rendered as if it were `false` (`null` is falsy, taking the same ternary branch as `false`) — a genuine, reproducible attribute-level hydration mismatch for exactly the population this code exists to accommodate, not a false-positive dev-mode warning. Confirmed by temporarily reverting only this file (`git stash push -- app/\(access\)/access/EntranceMotion.tsx`) and re-running the new regression test below against the unmodified code: React logs a real hydration-mismatch error, and the captured diff shows precisely this — the three silhouette `<svg>`s' server-rendered `style={{transform:"none"}}` (the motion-value-driven `{x, y}` style, evaluated at their default 0,0) diffing against the client's `style={{}}` (`undefined`, since the client already knows `shouldReduceMotion` is `true`), and the `<h2>`'s server-rendered `style={{opacity:"0",transform:"scale(0.96)"}}` (matching `initial={{opacity: 0, scale: 0.96}}`) diffing against the client's `style={{opacity:1,transform:"none"}}` (matching `initial={false}`, i.e. rendered pre-animated to its target). Restoring the fix (`git stash pop`) and re-running the same test passes clean. This mismatch is invisible to every existing test in this codebase: `tests/e2e/access-gate.spec.ts`'s own "respects prefers-reduced-motion" test already emulates reduced motion and navigates to `/access`, but only asserts the *settled* post-hydration CSS state (which is correct either way, since `useSyncExternalStore`'s corrective re-render happens before paint) — it never captured console output, so it could pass unchanged both before and after this fix without ever exercising the actual defect.

**Why `useSyncExternalStore` and not, e.g., a `useEffect` + `useState` pair:** `useSyncExternalStore`'s `getServerSnapshot` parameter is React's own documented mechanism for a value that must agree with the server on the very first client render but may differ from it thereafter — it guarantees the corrective re-render (once `getSnapshot`'s real value is read post-hydration) happens before the browser paints, not after, so there is no visible flash in addition to no console warning. A plain `useEffect`-driven `setState` would still fix the console warning (the first render would match SSR either way, since the effect hasn't run yet) but would let the entrance's `initial`/`transition` state visibly reflect the wrong (non-reduced) assumption for one paint before the effect corrects it — a strictly worse outcome than what `useSyncExternalStore` provides, for the same amount of code. This also fixes a smaller, secondary defect in the library hook it replaces: `motion/react`'s own `useReducedMotion()` never updates after mount even though it maintains a `change` listener internally (confirmed directly in its source — the listener updates the module-level ref but never calls a React state setter, and the hook's own inline comment reads `// TODO See if people miss automatically updating shouldReduceMotion setting`); the replacement's `subscribe` correctly re-renders this component if the OS-level setting changes while the page is open.

**Verification:** `pnpm typecheck`/`pnpm lint`/`pnpm format:check` all pass. A new regression test (`tests/e2e/access-gate.spec.ts`, "mounts under prefers-reduced-motion with no hydration-mismatch console warning") captures console/page errors under `emulateMedia({reducedMotion: 'reduce'})` and asserts none occur — confirmed to fail against the unmodified code and pass against the fix, per the live `git stash`/retest methodology above (mirroring D-044's own verification technique for this exact file). The full existing `access-gate.spec.ts`, `reduced-motion-audit.spec.ts`, and `custom-cursor.spec.ts` suites pass unmodified. The full unit suite (160/160) is unaffected (this hook has no unit-testable pure logic beyond what `lib/motion/media.test.ts` already covers).

**Also found during this verification, confirmed pre-existing and unrelated:** running the full Playwright suite surfaced two additional flaky failures beyond the two D-046 already documented — `custom-cursor.spec.ts`'s "activates only after a real pointer move is observed" and `homepage.spec.ts`'s "sets non-zero depth offsets after a real pointer move on desktop", both pointer-move/`requestAnimationFrame`-driven assertions. Isolated (`--workers=1`) each passes reliably (5/5); run concurrently with `--repeat-each=3` both fail consistently under the added system load. Confirmed unrelated to this change by the same A/B technique D-046 established: stashing this pass's entire diff and re-running the identical concurrent command against clean `main` reproduces the identical failure pattern. Extends D-046's existing observation (load-sensitive `requestAnimationFrame`/pointer-timing flakes in this suite) to two more tests in the same category rather than opening a new, unexplained one — not fixed here for the same reason D-046 gave: stabilizing flaky Playwright timing assertions is a test-engineering concern, not an accessibility one.

**Reason:** ROADMAP.md Phase 12's accessibility-pass line item was scoped to include reduced motion explicitly, and this exact defect was named as this pass's own concrete starting point (flagged but deliberately deferred by D-044, whose own brief was performance-only). Fixing it by replacing the problematic hook — rather than suppressing the warning (`suppressHydrationWarning`, which would leave reduced-motion users' actual first-paint content wrong, not just quiet the console) or reverting to the pre-D-044 full `motion` import (which would reintroduce the exact bundle-size regression D-044 fixed, and wouldn't fix the mismatch either — the bug is in `useReducedMotion()` itself, not in `LazyMotion`/`m`) — is the only option that actually resolves the underlying defect rather than trading it for a different one.

## D-049 — Interactive Model's info panel gains `aria-live="polite"`/`aria-atomic="true"` so activating a hotspot is announced to non-visual users

**Decision:** The panel container in `components/interactive-model/InteractiveModelExperience.tsx` (the `div` that renders either the empty-state prompt or `ActiveGarmentPanel`) now carries `aria-live="polite"` and `aria-atomic="true"`.

**Reason:** Activating a hotspot (Enter/Space, or a click) sets `activeRegion` state, which swaps this panel's entire content — but the panel sits in a different part of the DOM from the hotspot `<button>` that triggered the change, and nothing previously announced that a change had happened. A sighted mouse user sees the panel appear next to their cursor; a keyboard/screen-reader user who just pressed Enter on a hotspot had no way to know the panel updated short of guessing and tabbing forward to discover it — exactly the "live-region announcements where state changes without navigation" gap this pass's brief named explicitly for this component. `aria-atomic="true"` because the ternary swaps the region's entire subtree (empty prompt ↔ full garment panel), not a small in-place edit — the whole new content should be announced as one unit, not a diffed fragment. `"polite"`, not `"assertive"`: this is the direct, expected result of the user's own deliberate action, not an urgent/error condition, matching the non-disruptive tenor DESIGN_SYSTEM.md/CONTENT.md already establish for this codebase's other state-change feedback.

**Considered and excluded, with reasoning:** the task's other three named examples of this class of gap — filter results, Add to Bag, form validation errors — were checked and don't need the same treatment. `CategoryListing`'s filters (`FilterBar.tsx`) are plain `<Link>`s and a native GET `<form>`, producing a genuine full-page navigation on every change; the browser's own new-document/title/focus-reset behavior is the standard, sufficient signal for this case, not an in-place update needing a live region. Add to Bag (`ProductPurchasePanel.tsx`/`InteractiveModelExperience.tsx`) is a real, `onClick={() => {}}` no-op (D-016/D-029 — no cart exists yet) — there is genuinely nothing to announce. Form validation errors (`AccessForm.tsx`/`RequestAccessForm.tsx`) already use `role="alert"`, which is announced on insertion per the ARIA spec — the recognized, sufficient technique (WCAG's ARIA19) for exactly this case; see D-050 for the further, separate improvement made there.

**Verification:** live-verified through the same temporary fixture probe route described in D-048 — with the probe's fixture garments, the panel container carries both attributes from initial render (showing the empty-state prompt), and, critically, activating a hotspot via keyboard (`.focus()` + `Enter`, matching D-037's own verified keyboard interaction model exactly) correctly swaps in the real garment panel (a heading with the fixture product's title becomes visible) while the *same* element continues to carry `aria-live="polite"` — confirming this is a real, working live region around genuinely swapped content, not a static, disconnected attribute. `pnpm typecheck`/`pnpm lint`/`pnpm format:check` pass. No permanent automated regression test is added for this specific interaction: like D-045's `priority` fix, real end-to-end coverage is blocked by the same no-configured-Shopify-store limitation that keeps `InteractiveModelExperience` from ever mounting in this environment (`InteractiveModel.tsx` always falls back to `InteractiveModelPlaceholder` here — confirmed by `homepage.spec.ts`'s own "does not mount its real, interactive tree" test) — noted honestly as a gap rather than silently left, matching D-045's own precedent, rather than inventing a jsdom/component-test harness this codebase has deliberately never adopted (see `lib/product/recently-viewed.ts`'s header comment on the Node-only vitest environment) for one assertion.

## D-052 — D-026 re-investigated with fresh evidence (ROADMAP.md Phase 12 SEO pass): still unresolved, for a more precise reason; noindex mitigation stands

**Decision:** Per this file's "don't rewrite history" convention, D-026's text is left exactly as written. This entry records a fresh re-investigation performed specifically because current Next.js documentation (unavailable-in-substance, or at least not cited, when D-026 was written) names a mechanism D-026 never tried — and because re-asserting an old finding without re-verifying it against the current codebase and current docs would not meet this project's own evidentiary bar. The outcome is the same as D-026's (`/tops/[subcategory]` etc. still return HTTP 200 + `noindex` for an unknown subcategory, never a hard 404), but the reason is now understood more precisely, and one genuinely new mechanism was tried and empirically disproven rather than assumed to fail.

**What's new since D-026:** Next.js's current, version-matched bundled documentation (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/not-found.md`, confirmed installed at exactly 16.3.1) states: "With [Cache Components], every dynamic route streams a static shell first, so run that check in [`proxy`]instead" — i.e., checking resource-existence in Proxy (which runs before any React rendering/streaming begins) is Next's own documented fix for this exact problem, conditioned on a feature (Cache Components) this project confirmed is **not** enabled (`cacheComponents` defaults to `false`; `next.config.ts` sets no `experimental`/`cacheComponents` flag — confirmed by inspecting `node_modules/next/dist/server/config.js`'s compiled defaults directly, not assumed).

**Fresh empirical work performed, mirroring D-026's own real-`next start`-plus-`curl` methodology exactly (not just re-reading docs and assuming):**
1. Reproduced D-026's original finding fresh on current `main`: a real `pnpm build && pnpm start`, `curl -H "User-Agent: Googlebot" /tops/not-a-real-subcategory` → `200`, `noindex` present, branded UI present — unchanged.
2. Confirmed the comparison case still holds: `curl /this-route-does-not-exist` → real `404`, served from a build-time-precompiled static artifact (`.next/server/app/_not-found.html`, confirmed to exist) — Next's documented "non-streamed response" path.
3. Tried the new, genuinely untested (by D-026) avenue the current docs point to: modified `proxy.ts` to check subcategory validity via the already-available, zero-Shopify-dependency, synchronous `getSubcategoryProductType()` (`lib/catalog/taxonomy.ts`) and `NextResponse.rewrite()` a request for an invalid subcategory to a guaranteed-unmatched sentinel path, on the theory that Next's own "genuinely unmatched route" handling (confirmed real and working in step 2) would take over. Built and tested via real `next start`/`curl` in two variants:
   - Bare `NextResponse.rewrite(new URL('/__esque_404_test__', request.url))` → still `200`.
   - The same rewrite with an explicit status override — `NextResponse.rewrite(url, { status: 404 })`, confirmed via `node_modules/next/dist/server/web/spec-extension/response.d.ts` that `rewrite()`'s second parameter really is a typed `MiddlewareResponseInit extends globalThis.ResponseInit` accepting `status`, not a guess — → **also** still `200`.
   
   Conclusion, drawn from the response's own construction (`node_modules/next/dist/server/web/spec-extension/response.js`): `NextResponse.rewrite()` returns a signal object (`x-middleware-rewrite` header + whatever `init` was passed) that Next's server reads to decide *what to render*, not a literal response forwarded to the client — the destination still re-enters dynamic rendering, and *that* render is what ultimately commits the status the browser receives. A status set on the rewrite's own signal object doesn't survive to the real response. This is a materially different, and now directly tested, mechanism from D-026's three original attempts (all of which acted *inside* the page-rendering tree) and from its 4th isolated probe (a bare `notFound()`-only page, still inside that tree) — Proxy-level rewriting is a genuinely different lever, and it was tried, not assumed to fail.
   
   All experimental `proxy.ts` edits were reverted before this entry was written; nothing from this investigation shipped. `git status`/`git diff` confirmed clean before resuming the rest of this pass.

**Two further alternatives considered and rejected, with reasoning (not empirically tried, each has a decisive disqualifying property independent of whether it would work):**
- **Enabling Cache Components** (`cacheComponents: true`) — the only path Next's own docs actually promise will make a Proxy-level check produce a real 404. Rejected: this is a sweeping, app-wide rendering-model change (every dynamic route's caching/streaming contract changes, per `node_modules/next/dist/docs/01-app/02-guides/migrating-to-cache-components.md`), wildly disproportionate to fixing one soft-404 edge case, and would need re-auditing Phases 2-9's entire already-shipped, already-tested dynamic-rendering surface for a single, already-mitigated gap. Directly contrary to CLAUDE.md's "smallest architecture," "do not introduce unnecessary abstraction," and "respect existing architecture unless there is a strong technical reason to change it."
- **Reading Next's precompiled `_not-found` build artifact directly from Proxy** (Node runtime has full `fs` access; confirmed `.next/server/app/_not-found.html` exists and is a real, correct, byte-complete static file) and serving it with a genuine `status: 404` — mechanically plausible (a terminal, non-rewrite `NextResponse` fully controls its own status), but rejected: it depends on an **undocumented, internal build-output path** with no cross-version stability guarantee, and this project deploys to Vercel (D-003) — the exact packaging/availability of `.next/server/` internals inside a Vercel serverless function bundle is not a documented contract this code could rely on. This is precisely the "do not invent APIs... verify documented behavior" line CLAUDE.md draws, applied to relying on internals rather than a published surface.
- **A Proxy-level redirect** to a separate, fully-static "really doesn't exist" page (a genuine, terminal `NextResponse.redirect()`, which — unlike `rewrite()` — *does* fully control its own response and would trigger a fresh top-level request that could hit the real static-404 fast path) was also considered. Rejected on UX grounds, not a technical failure: it would change the browser's address bar away from the URL the visitor/crawler actually requested — a strictly worse outcome than today's branded 404 UI at the same URL, for a redirect-then-404 pattern Google's own guidance treats as valid but not preferred over a direct 404 on the original URL.

**Reason for still deferring rather than continuing to iterate:** The practical mitigation D-026 already identified remains genuinely in place and independently verified again this pass: the `noindex` tag is real, confirmed present in the actual response, and is Next's own documented, intentional safety net for exactly this case — a mistyped subcategory URL will not get indexed regardless of its status code. A fully correct fix, per Next's own current docs, requires adopting a sweeping rendering-mode change with no other justification in this codebase, or relying on unstable internals unsuited to this project's deployment target. Both are worse trades than leaving a well-mitigated, honestly-documented, now twice-investigated limitation in place. ROADMAP.md's Phase 12 SEO line is updated to point here in addition to D-026.

**Incidental finding, out of scope, flagged rather than silently discovered and dropped:** while curl-testing `/products/[handle]` under `next start` during this pass's own verification (unrelated to the D-026 mechanism above), a real product handle request against this environment's unconfigured Shopify client rendered the branded not-found UI (`THIS PIECE DOESN'T EXIST.`) rather than the expected error boundary (`SOMETHING WENT WRONG.`) that `tests/e2e/pdp.spec.ts` already asserts and that this exact route has always been documented to produce. Confirmed via `git stash` that this reproduces identically on unmodified `main` — not a regression from this pass. Not investigated to root cause (a plausible but unconfirmed candidate: `generateMetadata` and the page component both independently `await getCachedProduct(handle)`, which rejects for the same "Shopify not configured" reason on both calls; Next.js may handle a rejection surfaced through `generateMetadata` differently from one surfaced through the page body — this was not verified). Out of scope for an SEO-metadata/structured-data/sitemap pass; `pdp.spec.ts` itself runs against `next dev` (Playwright's `webServer`), where this discrepancy does not reproduce (confirmed: the full suite's existing PDP test still passes), so this is specifically a `next start`/production-build behavior gap, undiscovered until this pass's own D-026-style `next start`-plus-`curl` verification exercised it. Flagged here for whichever future pass next has reason to `curl`-verify the PDP under a production build, matching this project's D-046/D-047 precedent for recording an incidentally-found, unrelated defect rather than silently leaving it for someone else to rediscover.

## D-053 — SEO pass: metadata, canonical URLs, Open Graph, structured data, sitemap, robots.txt (ROADMAP.md Phase 12)

**Decision, in five parts:**

**1. Shared metadata helper (`lib/seo/metadata.ts`), canonical strategy.** `buildPageMetadata({title, description, path})` is the one place every real, indexable route builds its `title`/`description`/`alternates.canonical`/`openGraph` from — used by `/new`, `/tops`, `/bottoms`, `/etc` (static `metadata`) and their `[subcategory]` siblings plus `/products/[handle]` (`generateMetadata`). `path` is always the bare pathname, never a query string — category pages carry Sort/Availability/Price filter params (D-024) that vary the rendered list without creating genuinely distinct content; per current Google guidance on consolidating duplicate/near-duplicate URLs (fetched directly from `developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls` before implementing, not assumed from memory), the filtered variants correctly point back to one parameter-free canonical rather than each self-canonicalizing. The homepage has no page-level override — `app/layout.tsx`'s own `metadata` export (which also adds `metadataBase: new URL(SITE_URL)`, required before any relative URL-based field is used anywhere) doubles as `/`'s real, complete metadata, not just a fallback. `/access` keeps its existing `robots: {index: false}` (D-005: a UI gate, not indexable content) and gains a matching `alternates.canonical` for consistency. `app/not-found.tsx` gains a real title/description (Next already auto-injects `noindex` for any `notFound()`-triggered render — confirmed both against current docs and by this project's own `curl` output — so nothing further was added there); it gets no canonical, since a 404 has no one real URL to represent.

**2. Open Graph, and why every page explicitly re-declares the full object.** Verified against Next's current `generateMetadata` docs, not assumed: metadata merging **replaces** a parent segment's entire `openGraph` object the moment a child segment declares its own — a page that set only `{title, description}` would silently lose `siteName`/`type`/`locale`, not inherit them. `buildPageMetadata` therefore always emits the complete object (`siteName: 'Esque'`, `type: 'website'`, `locale: 'en_US'`, plus the page's own `title`/`description`/`url`). A genuine defect was caught and fixed *during this same pass*, before shipping: `og:image` was originally left out of this object entirely, on the (docs-text-literal) theory that "file-based [`opengraph-image`] metadata has higher priority and will override" whatever an object declares, making an explicit image field redundant. Empirical testing (`curl` against a real build — the same discipline used throughout, not trusting the doc sentence at face value) disproved this for this exact case: a route that declares *any* `openGraph` object of its own does **not** receive the ancestor's file-based image at all once that full-object replacement happens; only `/access` and `/` (both of which set no competing `openGraph.images`, or none at all) received it. Confirmed by direct `grep` on real response bodies before and after the fix. Fixed by having every page's `openGraph.images` explicitly re-reference the one sitewide image by its own conventional URL (`lib/seo/site.ts`'s `OG_IMAGE_PATH = '/opengraph-image'`, plus its known `width`/`height`/`alt`, duplicated as constants rather than imported from `app/opengraph-image.tsx` — `lib/` must not depend on `app/`, the reverse of every other dependency direction in this codebase; a comment flags the two files must be kept in sync if the image's size/alt ever changes). Re-verified afterward via a temporary fixture probe (`app/(storefront)/probe-og-temp/`, deleted before this commit — this Shopify-unconfigured environment cannot reach any real category/PDP page's success path to verify this live, the same D-023-class limitation every catalog-facing pass has hit) that the static build output for a page using `buildPageMetadata` carries a byte-correct `og:image` pointing at `/opengraph-image` with the right dimensions.

**3. The Open Graph image itself (`app/opengraph-image.tsx`).** No real product/campaign photography exists (PROJECT.md §101) — consistent with this project's placeholder-honesty standard (D-032/D-034: build the real mechanism now, never fabricate content that isn't real), this renders a plain brand card generated with `next/og`'s `ImageResponse` (ships with Next.js itself — no new dependency) from real, already-decided design tokens only: `--color-esque-black` background, the `ESQUE` wordmark in `--color-esque-text`, one restrained `--color-esque-forest` accent line (DESIGN_SYSTEM.md §5's "5% forest" rule). This is not a "PLACEHOLDER"-labeled stand-in the way, e.g., `SizeGuidePanel`'s measurements are — a text brand card is genuinely presentable, permanent content, not a simulation of a product photo that doesn't exist yet. No custom font is loaded (Satori/`next/og` needs font bytes loaded explicitly; this project's self-hosted `next/font/google` files aren't available in that form without new font-loading plumbing with no other consumer — YAGNI, the same reasoning D-029 already applied elsewhere); Satori's default sans renders the plain uppercase wordmark correctly. Verified via `curl`: a real 1200×630 PNG, confirmed with `file(1)` and by viewing the image directly.

**4. Structured data (`lib/seo/structured-data.ts`, `components/seo/JsonLd.tsx`).** Verified against Google's current structured-data guidance, fetched directly (`developers.google.com/search/docs/appearance/structured-data/product-snippet`) rather than assumed from memory: Product structured data requires `name` plus **at least one** of `review`/`aggregateRating`/`offers` — never all three, and review/rating are never required outright. This codebase has no reviews feature and never fabricates one; `offers` (built entirely from real, already-fetched Shopify fields — `minPrice.amount`/`currencyCode`, `variants[].availableForSale`) is what's used. `offers.availability` maps to schema.org's `InStock`/`OutOfStock` (confirmed current `ItemAvailability` enum members includes these) via `lib/product/variants.ts`'s already-existing, already-tested `isProductSoldOut` — no new availability logic invented. `image`/`description` are omitted from the JSON-LD object itself (not merely relying on `JSON.stringify` dropping `undefined` values, which was an inconsistency the unit tests caught and a follow-up fix corrected) whenever the underlying field is empty — never fabricated. No `sku`/`gtin`/`mpn`/`productID` is emitted: Shopify's internal GID is not a real SKU, and using it as one would be actively misleading, not merely absent. `BreadcrumbList` mirrors the real, existing navigable hierarchy — Home → category → subcategory (`CategoryListing.tsx`, shared by all seven category/subcategory routes) or Home → category → subcategory → product (`products/[handle]/page.tsx`, via a new `lib/catalog/taxonomy.ts` reverse lookup, `getCategoryForProductType`, extending rather than duplicating the existing category→productType taxonomy module; falls back to a shorter Home → product trail if a real store's `productType` string doesn't match a known subcategory, the same D-023-class caveat already documented, rather than erroring). This project has no visible on-page breadcrumb UI (DESIGN_SYSTEM.md never specifies one) — structured breadcrumbs don't require a visible match, only navigational accuracy, which this has. `JsonLd` renders via Next's own documented JSON-LD pattern exactly (`<script type="application/ld+json">` + `JSON.stringify(...).replace(/</g, '\\u003c')`) — not a general HTML sanitizer library, which would be the wrong tool for content that must contain zero HTML rather than some-tags-allowed HTML. Verified via a temporary fixture probe (`app/(storefront)/probe-pdp-temp/`, deleted before this commit) since the real PDP never reaches its success path in this Shopify-unconfigured environment (same limitation as D-023/D-028/D-030/D-034/D-045/D-048/D-049): the compiled static output contains byte-correct `Product` and `BreadcrumbList` JSON-LD against fixture data. 9 new unit tests (`lib/seo/structured-data.test.ts`) cover the pure builder functions directly (InStock/OutOfStock branching, image/description omission, no fabricated review/rating, breadcrumb positioning).

**5. Sitemap (`app/sitemap.ts`) and robots.txt (`app/robots.ts`).** Sitemap lists only routes that actually exist today: `/`, `/new`, and `/tops`/`/bottoms`/`/etc` plus their real subcategories, all derived from `lib/navigation-data.ts`'s `NAVIGATION` (the same single source of truth `lib/catalog/taxonomy.ts` and `Header`/`FullScreenMenu` already use) via an explicit allowlist of which top-level `NAVIGATION` entries correspond to built routes — `NAVIGATION` also lists `/collections` and `/about` (not built until later ROADMAP.md phases), which the allowlist deliberately excludes rather than 404-listing them; a comment flags that this allowlist needs a new entry the day either ships. Product PDPs (`/products/[handle]`) are **not** included — enumerating real handles needs a real Shopify store, the same D-016/D-023-class limitation every prior phase has hit and documented rather than guessed around; this is a deliberate, honest, partial sitemap, matching this project's established narrowing convention, not an oversight. `/access` is excluded (a UI gate, not content — D-005). Only `url`/`lastModified` are set per entry; `changeFrequency`/`priority` are deliberately omitted — Google has stated for years it does not use either for crawl scheduling or ranking, so setting them would be manufacturing unused signal, not adding real value. `robots.txt` allows everything (`userAgent: '*', allow: '/'`) and points to the sitemap. `/access` is **not** disallowed there, even though it's excluded from indexing: current Google guidance is explicit that `noindex` and robots.txt `Disallow` must never be combined for the same URL, since a disallowed page can't be crawled at all, so Google never sees the `noindex` directive that page's own metadata already sets, and a disallowed-but-linked URL can still surface in results with no snippet — the existing page-level `robots: {index: false}` is the correct, sufficient, already-in-place mechanism on its own. `proxy.ts`'s matcher already excluded `/robots.txt`/`/sitemap.xml` from the access-gate redirect in anticipation of this pass (its own comment said as much) — unmodified here, and reconfirmed correct by two Playwright tests.

**Verification (all five parts together):** `pnpm format:check`/`lint`/`typecheck` pass. `pnpm test:unit` — 177/177 (17 new: 4 taxonomy reverse-lookup, 4 metadata-helper, 9 structured-data). `pnpm build` succeeds; the new routes (`/sitemap.xml`, `/robots.txt`, `/opengraph-image`) all statically prerender (`○`), confirmed via the build's own route table. `pnpm exec playwright test` (full suite, both configured projects) — 178 passed, 6 skipped, 0 failed. One existing test (`tests/e2e/access-gate.spec.ts`'s "an ungated request to /robots.txt is not redirected to /access") had asserted `404` with an explicit comment noting it anticipated needing an update "once Phase 12 adds a real robots.ts" — updated to assert the now-correct `200` plus real content, and a matching new test added for `/sitemap.xml`'s identical proxy-exclusion contract. Every metadata claim in this entry was confirmed by direct `curl` against a real `pnpm build && pnpm start`, not inferred from source reading alone — canonical/OG/title/description tags inspected directly on `/`, `/tops`, `/tops/hoodies`; `robots.txt`/`sitemap.xml` content inspected directly; the OG image fetched and viewed directly; Product/Breadcrumb JSON-LD confirmed via the fixture-probe technique described above.

**Reason:** PROJECT.md §79's SEO requirements (indexable product/collection pages, descriptive metadata, canonical URLs, structured product data, XML sitemap, Open Graph data, crawlable site architecture) were entirely unaddressed before this pass — no canonical, no Open Graph, no structured data, no sitemap, no robots.txt existed anywhere in the codebase (confirmed by a repo-wide grep before starting). This closes every one of those gaps to the extent honestly possible without a real Shopify store, documents the one gap that genuinely isn't (PDP sitemap entries), and fixes a real defect (the og:image inheritance assumption) caught by this pass's own verification discipline before it could ship silently broken.

## D-055 — Analytics wired (ROADMAP.md Phase 12): a typed, closed event taxonomy; GA4 via `@next/third-parties`; Search Console's real code surface; Shopify Analytics is genuinely automatic; real events wired at every interaction point this codebase can currently produce

**Decision, in six parts:**

**1. Core abstraction (`lib/analytics/`) — mirrors D-020's exact precedent: build the real mechanism now, defer only what needs a live third-party account.** `lib/analytics/events.ts` defines `AnalyticsEventName` as a closed union derived from one `as const` array (`ANALYTICS_EVENT_NAMES`) — a single source of truth for both the runtime allowlist and the compile-time type, so a typo'd event name is a type error at every call site, not a silent analytics gap (CLAUDE.md's Analytics section: "consistent documented event names and properties," required as code, not prose). Each event's property shape is independently typed in `EventPropertiesMap`, so an object-literal call site also gets TypeScript's excess-property check (an undeclared field is a compile error) and can't omit a required one. `sanitizeEventProperties` strips any top-level PII-shaped key (`email`, `password`, `firstname`, `lastname`, `phone`, `address`, `consent`; case-insensitive) before an event ever reaches a sink — defense-in-depth beyond the type system, for a value that reaches this function some other way (a spread, an `as` cast, a future refactor); every declared property shape in this codebase is checked and none of them ever include a denylisted key today. `isKnownAnalyticsEvent` + `dispatchAnalyticsEvent` add a second, runtime layer of the same closed-taxonomy guarantee and never throw (an unknown name is dropped; a throwing sink is swallowed) — CLAUDE.md's Analytics section and this task's own brief both require the whole mechanism to never block the UI.

`lib/analytics/gtag.ts` is the thin, browser-only adapter — `isAnalyticsConfigured()` (reads `NEXT_PUBLIC_GA4_MEASUREMENT_ID`) and `trackEvent()`, the one function every real call site uses. `trackEvent` no-ops (never throws) both outside a browser (`typeof window === 'undefined'` — true during SSR/RSC, and, incidentally, in this project's Node-only vitest environment too) and when GA4 isn't configured — exactly `.env.local.example`'s already-existing `NEXT_PUBLIC_GA4_MEASUREMENT_ID` placeholder, present before this pass began (ARCHITECTURE.md/ROADMAP.md already referenced it). Not fixed here: it isn't new, isn't worse at the newly-covered tiers than at the existing, already-tested `chromium` default, and re-litigating an already-reasoned-through Phase 3/D-014-era design choice is outside this task's actual scope (auditing the *newly added* tablet/laptop coverage).

**5. What it verifies well, and what this pass relied on: real layout/CSS response to viewport width and height, real DOM hit-testing/`clip-path` behavior, and real engine-level (WebKit vs. Chromium) rendering differences at each configured size.

**Reason:** ROADMAP.md Phase 12's "Cross-device QA (mobile/tablet/laptop/desktop)" is the last unchecked item in the entire phase sequence before V1.1/V2. The audit found the core commerce-adjacent responsive mechanisms (grid, PDP layout, Interactive Model, dialogs, Header, touch targets) already correct at the newly-covered tiers — a legitimate, well-verified outcome given this project's own established mobile-first build discipline (D-014 and its "same class of bug" precedent were the concrete risk this pass was watching for specifically, and no recurrence was found), not a sign the audit was shallow. ## D-057 — Demo Mode (`PREVIEW_DEMO_MODE`): a permanent, opt-in, off-by-default stakeholder-preview feature; reconciles with D-012/D-023/D-026/D-033's "never fabricate Shopify data" precedent

**Context.** The project owner asked to see the built site with real photography instead of the sitewide "ESQUE PLACEHOLDER" text markers (DESIGN_SYSTEM.md §65). A local-only preview mechanism was built on the spot: `PREVIEW_DEMO_MODE=1` in `.env.local` short-circuits `lib/shopify/products.ts`'s `getProduct`/`getProducts` to typed fixture data (`lib/shopify/preview-demo-fixtures.ts`) sourced from eight local stock photos (`public/preview-demo/*.jpg`), and swaps two homepage/Interactive-Model placeholder slots for that photography (`CollectionHero.tsx`, `SilhouetteIllustration.tsx`, threaded through `InteractiveModel.tsx`/`InteractiveModelExperience.tsx`). The project owner saw it, liked it, and — after being asked to confirm explicitly rather than this being assumed — asked for it to be made a **permanent, committed, documented feature**, not reverted. This entry records that decision and everything it required to harden responsibly: the architectural boundary, license/provenance verification, an image-optimizer root-cause investigation that overturned the original working theory, test coverage, and full validation.

**Decision, in five parts:**

**1. The architectural boundary — narrow, additive, off by default everywhere, never a production fallback.** Exactly two functions in one file (`getProduct`, `getProducts` in `lib/shopify/products.ts`) branch on the flag, both checking it as the very first statement, before `getStorefrontClient()` is ever touched — real-path behavior below that check is completely unmodified. Five more read sites exist purely to render the fixture content once it's fetched: `next.config.ts` (image-optimizer bypass, see Part 4), `CollectionHero.tsx` (hero image/campaign copy), `InteractiveModel.tsx` (reads the env var server-side and threads it as a prop), `InteractiveModelExperience.tsx` and `SilhouetteIllustration.tsx` (thread/consume that prop — a client component can't read a bare, non-`NEXT_PUBLIC_`-prefixed env var directly; it would always inline as `undefined`). Off by default everywhere, verified directly rather than assumed: `.env.local.example` documents the variable with an empty value (matching every other var in that file); `.github/workflows/ci.yml` never sets it; `playwright.config.ts`'s `webServer.env` never sets it (confirmed by reading both files — neither mentions `PREVIEW_DEMO_MODE`); no Vercel Production or Preview environment in this project sets it either, since nothing in this repository configures Vercel env vars at all — it would require a human to deliberately add it there. The check itself (`process.env.PREVIEW_DEMO_MODE === '1'`) is a strict-equality comparison against a literal `'1'`; an unset variable is `undefined`, which fails the check with no additional guard needed.

**Reconciling with D-012/D-023/D-026/D-033 — this does NOT reverse any of them.** This project has a strong, repeated precedent that a real page shows real data or an honest error/empty state, never fabricated Shopify data. Demo Mode does not weaken that precedent on the real path (flag off, true in CI/production/default local dev) — every real-path behavior D-012 (typed placeholder files over a mock client), D-023 (category pages query by `product_type`), D-026 (honest not-found handling), and D-033 (Selected Pieces' narrow, logged error-swallowing exception) established is completely untouched by this change, because the flag being off means the demo branches never execute at all. What Demo Mode adds is a *second, mutually exclusive, deliberately-flagged path* that a human must explicitly opt into locally — not a modification to what the real path does when Shopify is unconfigured or failing:

- **D-012** established typed placeholder data files over a mock Shopify client, reasoning that no real API shape existed yet to validate against. Demo Mode's fixtures share that *implementation shape* (a typed, hand-authored data file — `preview-demo-fixtures.ts`) but for a materially different *reason*: the real Shopify integration is fully built and exercised by every other test in this codebase; the fixtures exist to stand in for real photography during a specific, flagged, local preview session, not because the real data shape is unknown.
- **D-023** requires category pages to query the root `products` connection filtered by `product_type:"X"`. Demo Mode's `getProducts` short-circuit deliberately mirrors this exact query-string convention (filtering `PREVIEW_PRODUCTS` by whether the query string contains `"<productType>"`) so the real query-building code in `lib/catalog/filters.ts`/`lib/catalog/taxonomy.ts` and the Interactive Model's `lib/interactive-model/look.ts` needs no knowledge that it's talking to fixtures instead of Shopify — the contract is preserved, not bypassed.
- **D-026** is this codebase's investigated-and-mitigated soft-404 limitation (an unrecognized dynamic-route value returns HTTP 200 + `noindex` instead of a hard 404, in this Next.js version). Demo Mode's `getPreviewProductDetail` returns `null` for an unrecognized handle, exactly mirroring `getProduct`'s real not-found contract — a Demo Mode PDP request for a handle outside the six fixtures still renders the real `THIS PIECE DOESN'T EXIST.` UI (verified live, see Part 5) rather than a special-cased "always exists" fixture response. Demo Mode does not fabricate a product for every possible handle.
- **D-033** is a narrow, already-justified exception where `getSelectedPieces()` swallows a *real* Shopify error into an empty result, logged via `console.error`. Demo Mode is orthogonal to this, not an extension of it: it preempts the real-vs-error branch entirely by returning fixture data unconditionally when the flag is on, and D-033's own try/catch is never reached in that case. With the flag off — the state of every environment except a developer's own deliberately-configured machine — D-033's exception behaves exactly as originally decided, completely unaffected by Demo Mode's existence.

**2. Licensing — verified directly against Unsplash's current terms, not assumed from training data.** Fetched 2026-09-14. `unsplash.com/license`'s operative grant: images are usable "for free, including for commercial purposes, without permission from or attributing the photographer or Unsplash," subject to two restrictions — images can't be **sold** without significant modification, and photos can't be compiled to **replicate a similar or competing (stock-photo) service**. Esque's usage (eight images embedded as ordinary site imagery, behind an opt-in preview flag) triggers neither restriction. A provenance manifest (`public/preview-demo/SOURCES.md`) records this verification, a per-file table (dimensions, content description, whether a face is identifiable), and an honestly-disclosed gap: these files' individual Unsplash photo IDs/URLs were never captured at download time, and — checked directly (`sips -g all` for embedded metadata, a `strings` scan of each file for embedded credit/URL text) rather than assumed absent — none of the eight JPEGs carry recoverable EXIF/IPTC/XMP provenance either. Guessing a matching Unsplash URL from the image content was deliberately not attempted: a wrong guess would be confidently-fabricated provenance, a worse outcome than an honestly-disclosed gap. The manifest requires any future image added under this convention to record its source URL at download time.

**3. Identifiable people — a real, concrete consideration, not a theoretical footnote; flagged for the project owner's awareness.** Unsplash's copyright license covers the *photograph*; it does not clear the rights of people *depicted in* one. Per Unsplash's own Help Center (fetched directly, not assumed): "you are solely responsible to ensure that your use of the images does not violate or infringe third parties' rights, such as ... individuals depicted in the images, and obtain any necessary permissions from these third parties," and a model release exists specifically to permit "the use of [a person's] likeness for commercial purposes (to sell, promote, or endorse a product)." This was checked concretely, not assumed either way: **each of the eight files was viewed directly**, and six of the eight (`model-full.jpg`, `product-3.jpg` through `product-6.jpg`) show a clearly identifiable human face (recorded per-file in `SOURCES.md`); `hero.jpg` and `product-1.jpg` are cropped below the neck with no face visible, and `product-2.jpg` is a flat-lay with no person at all. Using a person's likeness to dress up a commerce-adjacent site's imagery sits close to the "promote a product" case model releases exist for. Demo Mode's narrow scope (opt-in, off by default, local-preview-only) meaningfully narrows this risk but does not zero it out — the same six photos would carry materially more exposure if Demo Mode were ever activated somewhere publicly reachable (a shared Vercel Preview URL, or a real deployment). Judgment call, recorded honestly: a clear, prominent, actionable caveat in both this entry and `SOURCES.md` — including an explicit "do not use beyond this narrow scope" instruction — is the right-sized response given the feature's actual current scope; it does not, on its own, warrant blocking this task or refusing to proceed, since the licensing question itself (can these photos be used commercially at all) is resolved, and the residual likeness consideration is a documented, bounded risk rather than an unresolvable one. **This is flagged explicitly for the project owner's own attention** (see the task's final report) rather than treated as fully closed by this entry alone — whether the current local-only scope is an acceptable risk tolerance, and what should happen before this ever reaches a shared or public URL, is ultimately the project owner's call, not an engineering one.

**4. Image-optimizer investigation — the original "no `sharp` installed" theory was wrong; found and fixed the real cause instead of installing an unnecessary dependency.** `next.config.ts` sets `images.unoptimized: true` when the flag is on. The working theory at the start of this hardening pass was that Next's built-in image optimizer failed to decode these JPEGs because `sharp` wasn't installed. Investigated properly rather than accepted at face value, per this task's own instruction to decide deliberately:

- **`sharp` is already installed.** `pnpm why sharp` confirms it as a real, resolved dependency — `next`'s own `optionalDependencies` entry, installed by pnpm into `next`'s private dependency tree (`node_modules/.pnpm/next@.../node_modules/sharp`), just not hoisted to the top-level `node_modules/sharp`. This is ordinary pnpm non-flat behavior, not a broken or skipped install — confirmed directly, not assumed from `sharp`'s absence at the repo root.
- **The real failure happens before any decoder — sharp or otherwise — is ever invoked.** Read `next/dist/server/image-optimizer.js` directly: the "isn't a valid image... received null" error fires from `detectContentType()`, a magic-byte sniff (checking for JPEG's `0xFF 0xD8 0xFF` header, etc.) that runs *before* `imageOptimizer()` reaches its `require('sharp')` call. `upstreamType` is `null` specifically when the fetched buffer's first bytes don't match any known image signature — meaning the buffer being sniffed wasn't JPEG data at all, regardless of what decoder might eventually process it.
- **Root cause: `proxy.ts`'s access gate intercepts the optimizer's internal loopback fetch for local images.** Next's image optimizer fetches a *local* `/public` image via an internal server-to-server "mocked request" (`fetchInternalImage`), re-entering the app's own request-handling pipeline rather than issuing a real HTTP request. That synthetic request carries neither this app's access cookie nor a user-agent `isbot()` recognizes as a crawler, so `proxy.ts` (ARCHITECTURE.md §6, D-005/D-018/D-019) redirects it to `/access` exactly as it would a cookie-less human visitor — the optimizer receives that redirect/HTML instead of JPEG bytes. **Reproduced directly, not inferred:** with `unoptimized` temporarily removed and the dev server's own image optimizer exercised live, requesting `/_next/image?url=%2Fpreview-demo%2Fhero.jpg&...` returned HTTP 400 with the exact "isn't a valid image... received null" server log; a plain `curl` to the *static* path `/preview-demo/hero.jpg` (no optimizer involved) returned the real image because `isbot()` classifies bare `curl`'s default user-agent as a bot, bypassing the gate — a fact this codebase's own D-054 already documented for an unrelated check, re-confirmed here; a **spoofed real-browser user-agent with no access cookie**, requesting that exact same static path directly, was 307-redirected to `/access`; the identical request *with* the access cookie returned 200. This isolates the mechanism precisely: any cookie-less, non-bot-classified request to a path `proxy.ts`'s matcher doesn't exempt gets redirected, and the optimizer's internal loopback request is exactly such a request. This codebase's only `next/image` consumer before Demo Mode (`ProductCard`, real Shopify photography) always used a remote `cdn.shopify.com` URL — a completely different code path (`fetch` to an external host, never touching `fetchInternalImage`/`proxy.ts` at all) — so this interaction had genuinely never been triggered before Demo Mode's local `preview-demo/*.jpg` images existed.
- **Decision: keep `unoptimized: true`, scoped to the flag; do not add `sharp` as a dependency.** Adding `sharp` would fix nothing — it's already present, and the failure occurs upstream of where it would ever be invoked. The structurally "complete" fix — exempting local static asset paths from `proxy.ts`'s matcher, so real local-path `next/image` usage would work everywhere — was considered and rejected: it means changing a security-relevant access-control boundary (the access gate) to benefit a narrow, off-by-default preview convenience with no other current consumer, which is a worse trade than the zero-risk alternative actually available. `unoptimized` resolves to `undefined` (not `false`) when the flag is off, so Next's default optimizer behavior — and real Shopify photography via `remotePatterns` — is untouched at every other time. **Flagged for whoever next adds a real (non-Demo-Mode) local-path `next/image` consumer:** this exact interaction will reproduce for that usage too, and `proxy.ts`'s matcher is the place to fix it then, with the scrutiny a security-boundary change deserves.

**5. Test coverage — unit tests for the pure fixture logic and the demo-mode branches; E2E deliberately not added, with reasoning.** `lib/shopify/preview-demo-fixtures.test.ts` (new, 7 tests) covers `getPreviewProductDetail` directly: null for an unrecognized handle, a full `ProductDetail` shape for a known one, a sold-out fixture correctly mapping to an unavailable/zero-quantity variant (not fabricated availability), and every fixture handle resolving to a non-null detail — plus light structural invariants on `PREVIEW_PRODUCTS` itself (unique handles, every product has an image, at least one sold-out fixture exists for scarcity-UI coverage). `lib/shopify/products.test.ts` gained two new `describe` blocks (7 tests) covering the actual short-circuit branches in `getProduct`/`getProducts`: both never call `getStorefrontClient` (asserted via a before/after call-count comparison on the shared spy, since this file has no `restoreMocks`/`clearMocks` config and every earlier test's spy calls otherwise accumulate); `getProducts` respects `first` (a direct regression test for the real, previously-reproduced layout bug where omitting it fed `SelectedPieces` all 6 fixtures instead of 3); filters correctly by the `product_type:"X"` query string, including a specific check that "Shirts" and "T-Shirts" aren't conflated by the filter's substring-based matching (reasoned through, not just tested optimistically — verified the two query strings can't accidentally substring-match each other given how they're quoted); and falls back to the full fixture list (rather than an empty page) when a query matches no fixture's product type, documenting the short-circuit's actual current behavior rather than a specification for it.

**E2E coverage of the demo-mode-ON path was considered and deliberately not added.** `playwright.config.ts` has one shared `webServer` for the entire suite, booted once with one fixed `env` block — there is no per-test or per-file mechanism to flip `PREVIEW_DEMO_MODE` for a subset of specs against that same running server. The only ways to get real Playwright coverage of the flag-on path would be: a second, parallel `webServer`/project configuration (doubling the suite's server-boot overhead and adding a second config to keep in sync, for a feature with no other consumer); running the entire existing suite twice, once per flag value (doubling CI time for every existing test to gain coverage of a handful of demo-specific assertions); or a separate, narrow, manually-run config outside the main CI path (real, ongoing maintenance surface for a non-customer-facing convenience feature). None of these are proportionate to what they'd buy: Demo Mode touches no auth, cart, checkout, or payment logic; its actual branching logic is now covered deterministically and fast by the unit tests above; and its one remaining real risk — "does the browser actually render the image correctly" — is best verified by looking at it, which this pass did directly (Part 6) rather than through a brittle screenshot-diff assertion. This mirrors this project's own established precedent for exactly this kind of proportionality call (D-025 declining to fixture-test predictive search's actual value proposition; D-045/D-049 documenting a real coverage gap honestly rather than inventing a disproportionate test harness to close it) rather than over-engineering coverage for a narrow, low-risk, non-default feature.

**6. Verification.** `pnpm format:check`, `pnpm lint`, and `pnpm typecheck` all pass clean on the integrated diff. `pnpm test:unit` — **218/218 passed** (27 test files; 204 pre-existing plus 14 new — 7 in `preview-demo-fixtures.test.ts`, 7 added to `products.test.ts`). `pnpm build` succeeds with `PREVIEW_DEMO_MODE` unset (a true default-env baseline — `.env.local` was moved aside entirely for this run, not just overridden, to match what a fresh CI checkout actually sees) and again with the flag set, producing an identical route table both times (Demo Mode changes no route's static/dynamic rendering classification). `pnpm test:e2e` against that same true default-env baseline: **484 passed, 15 skipped, 1 failed** — the failure (`access-gate.spec.ts`'s "cursor parallax moves silhouette layers", `tablet` project) is `EntranceMotion.tsx`'s pointer-move-driven access-gate parallax, a file and feature this pass never touched. Confirmed unrelated via this project's own established A/B technique (D-046/D-047/D-050): isolated with `--repeat-each=5` against this pass's working tree, it failed 1/5; the identical command against unmodified `main` (this pass's entire diff stashed away, confirmed via `git status`) failed 2/5 — reproducing at least as often on a totally clean baseline, conclusively ruling out this pass's changes as the cause. Extends this codebase's already-long-running list of pre-existing, load-sensitive pointer/timing flakes (D-046, D-047, D-050) rather than opening a new, unexplained one; not fixed here for the reason those entries already gave — stabilizing flaky Playwright timing assertions is a test-engineering concern, out of scope for this pass.

A real functional check with `PREVIEW_DEMO_MODE=1` was performed twice — against `next dev` and again against a full `next build && next start` — rather than trusting that it still worked after this pass's edits. Both confirmed, via direct `curl` against the running server (a bot-classified user-agent, matching this codebase's own established D-054 verification technique, bypasses the access gate without needing the real login flow): the homepage renders `hero.jpg` and the campaign copy "AN EXERCISE IN RESTRAINT.", and the Interactive Model's two hotspots resolve to two genuinely distinct fixture products (`aria-label="Top — Featherweight Crewneck Sweater"`, `aria-label="Bottom — Tailored Wide-Leg Trouser Set"` — confirming the previously-fixed hotspot-collision bug stays fixed); `/new` renders real fixture products; the PDP for a known fixture handle returns the correct title/price/image, while an unrecognized handle still renders the genuine `THIS PIECE DOESN'T EXIST.` UI rather than a fabricated fallback; every demo image request returned the exact on-disk byte count with zero `/_next/image` optimizer calls for any `preview-demo/*` path (confirming the `unoptimized` bypass fully avoids the `proxy.ts` interaction described in Part 4); and the dev server's console showed no errors throughout.

**Reason:** The project owner's explicit instruction — after being asked to confirm rather than this being assumed — was to make this a permanent, committed, documented feature rather than reverting it. Doing that responsibly meant treating it with the same rigor this project applies to every other durable decision: verifying the licensing claim rather than assuming it, investigating the actual root cause of a workaround rather than reaching for the first plausible fix, reconciling explicitly with this codebase's hard-won "never fabricate Shopify data" precedent rather than quietly setting it aside, and validating the integrated result completely rather than trusting that code which "worked before" still works after every comment and test was added around it.

**Reaffirmed 2026-09-14:** Part 3's identifiable-people flag was raised explicitly for the project owner's own attention rather than treated as fully resolved by documentation alone. Project owner confirmed directly: these photos are for their own local use to demonstrate the built features, not for any real/public/shared deployment. No change to Demo Mode's scope or this entry's content — the same narrow, opt-in, off-by-default boundary already recorded above continues to be what makes this an acceptable risk; this note just records that the owner-level call Part 3 asked for has been made.

## D-058 — Predictive full-screen search (ROADMAP.md Phase 4): resolves D-025; `predictiveSearch` for products, local taxonomy matching for categories, COLLECTIONS/a results page/shared-element transitions all deliberately not built

**Context.** D-025 deferred search in full, reasoning that the mechanism (a real, typed Shopify query) could be built and verified without a store, but relevance/ranking quality could not. This entry resolves that deferral: the full-screen overlay (DESIGN_SYSTEM.md §50), a debounced input, a real `predictiveSearch` query, real local taxonomy matching, keyboard operability mirroring `FullScreenMenu`'s reviewed accessibility mechanics, and honest loading/empty/error states are built and verified against a typed client and fixture data. Relevance/ranking against a real, populated catalog remains exactly as unverifiable as D-025 said — this entry does not claim otherwise. Full design reasoning lives in `docs/superpowers/specs/2026-09-18-search-design.md`; this records the durable decisions and what an integration review found.

**Decision, in eight parts:**

**1. Query mechanism — `predictiveSearch`, verified against this project's own pinned schema, not assumed from D-025's two-month-old characterization.** `lib/shopify/queries/products.ts` gains `GET_PREDICTIVE_SEARCH_QUERY`; `lib/shopify/products.ts` gains `searchProducts(query, options?)`. Re-verified directly against `lib/shopify/storefront-2026-07.schema.json` (this project's actual pinned schema, the same file its codegen validates against — a stronger source than generic docs) before writing any query text: `predictiveSearch(query: String!, limit: Int, limitScope, searchableFields, types, unavailableProducts): PredictiveSearchResult` is real, with `products: [Product!]!` a plain (non-paginated) list. The `query` argument receives the user's raw, trimmed input **unmodified** — no wildcard, no `field:"value"` clause syntax (a deliberately different construction path from `lib/catalog/filters.ts`'s `buildProductSearchQuery`, which targets the different root `products(query:)` connection). Evidence: the schema's own field description states plainly that `predictiveSearch` "matches products... based on partial search terms" as inherent behavior; the general search-syntax reference (`shopify.dev/docs/api/usage/search-syntax`, fetched directly) never mentions `predictiveSearch` at all and confirms prefix matching on *that* grammar needs an explicit `*`; the plain `search` root query (unused here) has its own separate `prefix` argument for opting into partial-word matching, confirming its own default is exact-term matching — further evidence `predictiveSearch`'s partial matching is a distinct, inherent property of that field, not something to be manually replicated. `types: [PRODUCT]` is hardcoded in the query document (not a variable — this call site never varies it); `searchableFields`/`unavailableProducts` are deliberately **not** overridden — the schema's own description for `searchableFields` states outright "For the best search experience, you should search on the default field set," and `unavailableProducts`' documented default (`LAST`) already matches this site's own established never-hide-sold-out-inventory pattern. `limit: 6` (schema max 10) is a deliberate restraint choice matching DESIGN_SYSTEM's minimal aesthetic, not a field limitation.

**2. Categories — real, local, zero-I/O, no Shopify round-trip.** `lib/catalog/taxonomy.ts` gains `searchCategories(query, limit = 6)`, matching the user's query against `NAVIGATION`'s own category/subcategory labels (case-insensitive substring, checked independently at both levels) — verified to produce exactly DESIGN_SYSTEM.md §50's own worked example ("hoo" → `TOPS / Hoodies`, and only that). `BUILT_CATEGORY_HREFS` (which routes are real) is relocated from `app/sitemap.ts` into `lib/catalog/taxonomy.ts` — the module that already owns every other piece of `NAVIGATION`-derived logic, and the correct side of the `lib/` must-not-depend-on-`app/` rule (D-053) — rather than search reading a second, independently-drifting copy of the same knowledge; `app/sitemap.ts` now imports it, with no change to its own behavior/output. Because this is pure computation, it runs synchronously in the client component on every keystroke (`useMemo`, not an effect) and needs no Demo Mode branch at all — it is unaffected by whether Shopify or Demo Mode is configured, in either state.

**3. `COLLECTIONS` is deliberately not built as a third result group,** despite DESIGN_SYSTEM.md §50 naming one. Two independent, sufficient reasons: no `/collections/[handle]` route exists anywhere in this codebase (ARCHITECTURE.md §3 still lists it unbuilt) — a collection result would have no honest destination — and only one real collection exists in the committed launch catalog, the same "nothing to prove this isn't just returning everything" reasoning D-024 already used to defer a Collection *filter*, now applied to a new surface. `predictiveSearch` is queried with `types: [PRODUCT]` only; Collections/Pages/Articles are never requested, not silently dropped after being fetched.

**4. Overlay mechanics mirror `FullScreenMenu.tsx` exactly rather than reinventing them** — the same `role="dialog"`/`aria-modal` container, the same `hasOpenedRef`-gated open/close effect (focusing the `<input>` instead of a link, per DESIGN_SYSTEM.md §50's "input receives immediate focus"), the same `useEffectEvent`-based pathname-close effect, and the same hand-rolled Tab-cycle focus trap + Escape-to-close (the focusable selector widened to include `input:not([disabled])`, since this dialog's first focusable element is a text field). A new `.esque-search-overlay`/`[data-open='true']` CSS class pair in `app/globals.css` deliberately duplicates `.esque-menu`'s ~15 lines of identical visibility/opacity timing rather than sharing a class with it — `FullScreenMenu.tsx` is already-shipped, independently reviewed code, and coupling an unrelated new dialog to its class name is a worse trade than the duplication. One deliberate addition beyond `FullScreenMenu`'s own pattern: a real, visible `CLOSE` button — `FullScreenMenu` never needed one because every visible thing in it is a navigable link (clicking any category both navigates and closes); Search's primary content is an input plus result sections that can be empty, loading, or erroring, so there is no guaranteed clickable escape route for a mouse/touch user who hasn't discovered Escape.

**5. `app/api/search/route.ts` — this codebase's first Route Handler.** A client component cannot call `searchProducts()` directly (Shopify access is server-side only everywhere else in this codebase); a live, debounced, cancelable-via-`AbortSignal` read is a different responsibility from this project's existing Server-Action call sites (discrete form submissions), so a plain `GET` Route Handler fetched with a real `AbortSignal` is the idiomatic tool, not a second competing pattern for form-submission's job. Already excluded from the access gate with zero `proxy.ts` changes needed: its matcher already excludes `/api` unconditionally, with a comment anticipating exactly this ("route handlers, if any need to bypass the gate"). Confirmed directly against this project's installed Next 16.3.1 docs (`node_modules/next/dist/docs/.../route.md`): "the default caching for `GET` handlers was changed from static to dynamic" as of `v15.0.0-RC` — no `export const dynamic` override needed; confirmed in the production build's own route table (`ƒ /api/search`, dynamic). The caught error's real message is logged server-side only (`console.error`) and never forwarded to the client response (`{ error: 'search_failed' }`, generic), mirroring `app/error.tsx`'s own "log the real error, never show it" contract. `MAX_QUERY_LENGTH` (100) is defensive input hygiene, not a security boundary — `query` is a real GraphQL variable, never string-concatenated, so there is no query-injection surface regardless of its content.

**6. `enableSharedTransition` is deliberately left at its default (`false`) on search-result `ProductCard`s — a second, concrete instance of the exact collision D-038 first identified, not a hypothetical one.** `SearchOverlay` is mounted inside `ShellClient`, present on every page at once. If a visitor opens Search while already on a category page (whose grid renders every card with `enableSharedTransition` on) and a predictive result resolves to a product already visible in that page's own still-mounted (merely `inert`-covered, not unmounted) grid, enabling the transition on the search result too would mount two `<ViewTransition>` components with the same `name` simultaneously — the same "will cause View Transitions to error" failure D-038 already reproduced and built `ProductCard`'s opt-in default specifically to prevent.

**7. Search-products errors are caught and scoped inside `SearchOverlay`, deliberately not propagated to `app/error.tsx`.** Two genuinely different failure surfaces are kept genuinely different: a category-page/PDP Shopify failure correctly propagates to the page-level boundary today, because the commerce data *is* that page's entire reason for existing (ARCHITECTURE.md §1). `SearchOverlay` is mounted on every page simultaneously — letting a search failure crash whatever page the visitor happened to have open would be a wildly disproportionate blast radius for a self-contained utility widget failing. This is **not** the same shape as D-033's exception (which suppresses a real error into a silent, indistinguishable-from-empty result): the error here stays fully visible, distinguishable from "no results" (`NOTHING MATCHES.` and the error state are mutually exclusive, per PROJECT.md §87's own distinct copy for each), and actionable via a real `Retry` — it is simply scoped to the failing subtree instead of the whole document, the correct boundary for an always-mounted, cross-page widget.

**8. Analytics and Demo Mode.** `lib/analytics/events.ts` gains `search: { search_term: string; result_count: number }`, reusing GA4's own standard recommended event exactly where it is an honest match (D-055's own test for `view_item`, applied again here — verified directly against Google's current GA4 recommended-events reference: `search`/`search_term` is real and required, not invented). `result_count` folds PROJECT.md §82's "no-result searches" into this event's own payload rather than a second event (the same minimal-modeling choice D-055 made for `view_item`'s `sold_out` boolean), computed as `products.length + categoryResults.length` — exactly what the UI itself treats as "nothing matches," so the analytics signal and the visible empty state can never disagree. Fired once per settled (debounced, resolved) query, never per keystroke. `searchProducts` gets the same `PREVIEW_DEMO_MODE` short-circuit `getProduct`/`getProducts` already have, filtering `PREVIEW_PRODUCTS` by title/productType — with the opposite empty-query fallback from `getProducts`' own Demo Mode branch (returns `[]`, not the full fixture list, on no match), deliberately, since a real "no results" state is exactly what this feature must be able to demonstrate.

**Integration review — two real, small defects found and fixed before this shipped, neither changing the architecture above.** Per this project's established convention (D-037, D-043, D-047, D-051) of live-reproducing and fixing genuine findings before declaring a phase done, rather than reporting them as advisory:

- **Focus-ring inconsistency with D-010.** The search `<input>` originally shipped with `outline-none` and only a `focus-visible:border-esque-text` color change as its sole focus indicator — confirmed by a full-codebase grep to be the only `outline-none` anywhere in this project, diverging with no stated reason from the sitewide `outline-esque-text`/`outline-2`/`outline-offset-2` ring D-010 established (with its own computed WCAG 1.4.11 contrast verification) and that `Input.tsx` — the closest existing analog, a full-width bordered text field — already applies on top of, not instead of, its own equivalent border-color change. **Fix:** the standard focus-ring utilities were added alongside the existing border-color change, `outline-none` removed. `pnpm typecheck`/`lint`/`format:check` and the full Playwright suite (521 passed, 15 skipped, 0 failed) confirmed clean after the fix.
- **Stale cross-session content flash.** `productsState` was reset nowhere on close (only `query` was) — closing the overlay after a settled search and reopening it to type a *new*, unrelated query could briefly surface the *previous* session's results or error for the ~200ms debounce window, before the new fetch's `loading` state overwrote it. Within one continuous open session, brief staleness during ordinary debounce+edit (the previous query's results remaining visible for one debounce window while a new one resolves) is normal, common, acceptable debounced-search behavior and was correctly left alone — the defect is specifically the *cross-session* case, where the surfaced content belongs to an entirely different, already-closed search. **Fix:** `productsState` is now reset to `{ status: 'idle' }` alongside `query` in the same close-transition branch of the existing open/close effect — a real side effect of that transition (like the `.focus()` call already there), not an effect whose only job is mirroring state, so it does not reintroduce the `react-hooks/set-state-in-effect` shape the debounced-fetch effect's own early return was already written to avoid (confirmed: `pnpm lint` stayed clean after adding it).
